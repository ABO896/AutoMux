<objective>
Close the single BLOCKER gap in 09-VERIFICATION.md (CR-01): the per-macro running-state indicator never shows "held" for a Hold-mode macro created through the app. `computeRunningState` (src/App.tsx:90-107) infers held/firing purely from the persisted `sequence.steps` shape, but the only wired creation path (`handleCreateMacro`, src/App.tsx:460-472) always persists a single `InterleavedInterval` step regardless of the selected `trigger_mode`, and the scheduler's Hold->SustainedHold conversion (scheduler/mod.rs:287-294) is ephemeral — never written back to `AppState` (`Intent::AddMacro`, state/mod.rs:468, stores the config verbatim). Net effect today: every Hold-mode macro shows the pulsing green "firing" dot instead of the static accent "held" dot; the held/combined branches are unreachable in practice. This directly breaks plan 09-02's D-02 must-have.

**Fix approach — evaluated both candidates from 09-VERIFICATION, chose derivation-only:**
- **Approach A (chosen) — branch computeRunningState on `trigger_mode === "Hold"`.** Display-only; mirrors the scheduler's runtime conversion. No persistence change, no backend touch.
- **Approach B (rejected) — persist the Hold->SustainedHold conversion in `Intent::AddMacro`.** Rejected because converting `InterleavedInterval` to `SustainedHold` drops the step's `interval_ms` (data loss if the user later switches the macro back to Pulse or calls `update_step_interval`, which only mutates InterleavedInterval steps), and it changes backend behavior — contradicting D-04 (frontend-only derivation, no backend field, no behavior change). Approach A keeps the persisted step (with its `interval_ms`) intact and keeps the scheduler as the single source of truth for what is actually injected.

Also folds in WR-01 (non-blocking warning): `computeRunningState(macro, state()!)` is currently called 3 separate times per card (src/App.tsx:1233, 1248, 1253). Since this plan makes the function's logic branchier (adds the trigger_mode branch), the drift risk WR-01 warns about grows, so it is worth eliminating now by computing once per card as a reactive thunk and reusing it — the exact fix the review recommends.

Purpose: Make the running-state indicator honest for Hold-mode macros so the phase's D-02 UI deliverable actually works and the pending device tests (09-VERIFICATION §5/§6) observe the correct dot.
Output: A one-branch logic fix in `computeRunningState` plus a compute-once-per-card refactor of the macro-card render. Entirely within src/App.tsx; no new symbols, no backend change, no new dependencies.

**Out of scope:** No backend change (Intent::AddMacro / scheduler stay as-is). No new field on AppState (D-04). No new signal/createMemo. No frontend test framework is added (none exists — CLAUDE.md; behavioral correctness is proven by source assertion + tsc/build + the documented visual human-check). The 3 macOS device tests (T9.1–T9.3) and 3 Windows device tests (6.1–6.3) in 09-VERIFICATION.md stay as pending human verification — not planned here.
</objective>
