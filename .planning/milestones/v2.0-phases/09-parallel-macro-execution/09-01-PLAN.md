<objective>
Prove and harden the scheduler's parallel-execution capability. The single-scheduler BTreeMap timeline already supports multiple macros in principle (per-macro RunningConfig keyed by macro_id, CR-04 no-op restart); this plan (a) adds the unit tests that PROVE concurrent execution and independent stop, (b) raises the action-channel capacity for the higher parallel fire rate, and (c) adds a debug-only drop counter + IPC accessor so overflow is diagnosable rather than silent.

Purpose: Deliver the unit-level proof for EXEC-01/EXEC-02 and remove the action-channel overflow risk that parallel execution amplifies (flagged in CONCERNS.md).
Output: Two new #[tokio::test] functions, a debug-only drop counter, and a debug-only IPC command — all additive, no changes to the input-injection path.

**Out of scope (do NOT implement — deferred by CONTEXT decisions):**
- Per-macro re-evaluate optimization replacing the full-sweep reevaluate_all_macros (D-12)
- Debouncing of rapid mutations (D-13)
- Tightening CR-04's no-op detection (D-14)
- Any new field on AppState for firing state (D-04 — derivation is frontend-only, plan 09-02)
- Drop counter on state_tx / sched_tx channels (D-11 — action_tx only)

**Flagged assumptions (spec-less probe fallback):** EXEC-01 and EXEC-02 came back `unclassified/unresolved` from the edge-probe engine (the one-line requirement text is far less specific than CONTEXT.md's decisions). They are surfaced as `verification: backstop` truths above rather than dropped; the concrete acceptance criteria are the D-05–D-08-derived truths (the scheduler tests) plus the on-device manual tests in plan 09-03.
</objective>

<assumption_delta_decision>
- **Noun:** "the running macro" (singular) vs "running macros" (a set).
- **Decision:** no-change.
- **Rationale:** The codebase is already plural-shaped. The scheduler keys every timer by `StepId { macro_id, step_index }` and merges all macros into one `BTreeMap<Instant, Vec<StepId>>` timeline; `running_configs` is a `HashMap<Uuid, RunningConfig>`; `AppState.macros` is a map keyed by id; the CR-04 no-op guard operates per-macro. No singleton "the one running macro" field exists anywhere to promote. Phase 9 PROVES and SURFACES the existing plurality (via these tests and the per-card running-state in plan 09-02) rather than introducing a new plural representation. D-04 confirms the frontend derives per-macro state from existing per-macro fields, not from a new singular field. No representation change is warranted.
</assumption_delta_decision>

Assert with bounded ranges (Pattern P-3), never exact counts or timing assertions.

    Test 1 — `parallel_two_macros_concurrent` (D-06a): macro A interval 50ms, macro B interval 80ms. Send `SchedulerIntent::StartMacro` for A then B back-to-back, `tokio::time::sleep(Duration::from_millis(500))`, then `StopMacro` both, drop intent_tx, await, drain. Assert A's count is in a bounded range around 500/50=10 (e.g. >=5 and <=16) AND B's count is in a bounded range around 500/80=6 (e.g. >=3 and <=11), each asserted independently. The two independent non-zero ranges are what prove neither macro blocked the other. Choose bounds tight enough that a serial implementation (which would roughly halve one or both counts, or make them mutually exclusive) would fail — document the chosen bounds' reasoning in a code comment.

    Test 2 — `parallel_stop_one_keeps_other` (D-06b): macro A and macro B both at 50ms. Start A and B, `sleep(200ms)`, `StopMacro(A)`, `sleep(300ms)` more, `StopMacro(B)`, drop intent_tx, await, drain. Assert A's fire count is bounded to its ~200ms window (e.g. <=10) while B's count reflects the full ~500ms window (e.g. >=6) — B's count must be meaningfully greater than A's, proving stopping A did not stop B.

    If either test FAILS, that reveals a genuine parallel-execution defect in the scheduler (not a test-bounds problem) — fix the scheduler, do not loosen the assertion to make a serial implementation pass.
