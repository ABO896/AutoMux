<objective>
Make parallel execution visible per macro. Today the card shows only a binary enabled/disabled dot, so a user cannot tell "I enabled this — why isn't it firing?" This plan adds a pure frontend derivation (computeRunningState) that mirrors the backend's 3 injection gates plus a hold/interval distinction, and renders firing / waiting / held / combined / disabled states on each macro card. This is the UI surface that lets a tester (and a user) confirm multiple macros are firing concurrently.

Purpose: Per-macro running-state visibility (the UI half of the phase) and the on-screen signal the plan 09-03 manual device tests rely on to confirm "both fire".
Output: A computeRunningState helper + RunningState type and updated card dot + "Waiting for…" subtitle, entirely additive and derived on the frontend.

**Out of scope:** No backend field for firing state (D-04). No global firing/waiting count summary (D-03). No new createSignal/createMemo — computeRunningState is a pure inline-called function (D-04, Pattern P-5). No dependency additions.

**Flagged assumptions (spec-less probe fallback):** EXEC-01/EXEC-02 were `unclassified/unresolved` from the edge probe; this plan carries the UI-visibility half of the phase and does not itself close EXEC-01/EXEC-02 (the scheduler tests in 09-01 and the device tests in 09-03 do). The running-state UI is the observable surface those device tests read.
</objective>

  <behavior>
    - engine off OR emergency_stop_active OR macro not enabled -> "disabled"
    - enabled + engine active + target_app is null (Global) or equals state.active_app, steps contain only InterleavedInterval (or empty legacy sequence) -> "firing"
    - enabled + engine active + target present and != active_app -> "waiting"
    - enabled + engine active + target matches + steps contain only SustainedHold -> "held"
    - enabled + engine active + target matches + steps contain BOTH SustainedHold and InterleavedInterval -> "combined"
    - empty sequence (legacy single-click fallback, see scheduler/mod.rs:257-270) -> "firing"
  </behavior>
  <action>
    Add a top-level `type RunningState = "firing" | "held" | "combined" | "waiting" | "disabled";` and a pure function `function computeRunningState(macro: MacroConfig, state: AppState): RunningState` placed near formatInputEvent/formatStep (before the App component body), following the pure-helper shape (no signals, no side effects, called inline in JSX per Pattern P-5). Implement the gates in this order: (1) if `!macro.enabled` return "disabled"; (2) if `!state.engine_active || state.emergency_stop_active` return "disabled"; (3) compute `matchesTarget = macro.target_app == null || state.active_app === macro.target_app`; if `!matchesTarget` return "waiting"; (4) if `macro.sequence.steps.length === 0` return "firing" (legacy fallback); (5) compute `hasHold` = any step has "SustainedHold" in it, `hasInterval` = any step has "InterleavedInterval" in it; if `hasHold && hasInterval` return "combined"; if `hasHold` return "held"; return "firing". Use the same `"SustainedHold" in step` / `"InterleavedInterval" in step` discriminant checks already used by formatStep. Confirm the exact field names on the AppState/MacroConfig interfaces (engine_active, emergency_stop_active, active_app, target_app, sequence.steps) by reading the interface definitions before writing — use whatever the existing TS interfaces declare.
  </action>
