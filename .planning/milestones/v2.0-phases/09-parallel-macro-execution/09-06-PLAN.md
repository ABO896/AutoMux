<objective>
Close the one remaining Blocker-severity verification gap for Phase 9 (09-VERIFICATION.md, truth #8 / 09-REVIEW.md CR-01): `Scheduler::start_macro`'s `SustainedHold` branch delivers `HoldStart` via fire-and-forget `try_send` and then runs `holds.push(*input)` unconditionally — so under action-channel saturation the scheduler's `active_holds` and the frontend's `computeRunningState` can both report a Hold-mode macro as "held" while the `HoldStart` was never delivered and nothing is physically pressed. This is the exact mirror-image of the release-side stuck-input bug that plan 09-05 already fixed on the `release_holds` path.

Fix it the same way 09-05 fixed the release side: convert the `HoldStart` send to guaranteed `.await` delivery (matching `release_holds` at 377-390 and `StopAll` at 214-234), and add a saturation regression test mirroring the existing `stop_macro_release_delivered_under_saturation`.

Purpose: A configured Hold-mode macro must actually fire under load — a macro shown as "held" must be physically holding its input, never a phantom. Directly upholds the project Core Value.
Output: A hardened `start_macro` HoldStart path and a new RED→GREEN regression test in `src-tauri/src/scheduler/mod.rs`. No new files, no new dependencies, no frontend change.

Scope note (multi-source coverage): GOAL (Phase 9 parallel execution), REQ (EXEC-01/EXEC-02), and CONTEXT (D-01..D-14) breadth are already COVERED and verified by executed plans 09-01 through 09-05. No RESEARCH.md exists for this phase (research was skipped; CONTEXT.md substituted). This plan covers ONLY the single MISSING item flagged by re-verification: the CR-01 asymmetric HoldStart reliability gap. The three ROADMAP success criteria (SC1/SC2/SC3) require human device-level testing on real macOS and Windows hosts and are explicitly OUT of scope here — they are tracked as behavior_unverified in 09-VERIFICATION.md and must not be automated, faked, or claimed as closed by this plan.
</objective>
