<objective>
Close CR-01 (the sole remaining code gap for Phase 9): on macOS, a macro whose hotkey was set or changed via the card-edit UI silently fails to toggle because a single keypress dispatches `Intent::ToggleMacroHotkey` TWICE (once per each of two independently-populated hotkey registries) and the two `mac.enabled = !mac.enabled` flips cancel out. Consolidate to a single hotkey registry so one keypress produces exactly one toggle.

Source-of-truth decision (made after reading both registries' full call graph — see `<decision_rationale>`): keep `HOTKEY_BINDINGS`, remove `MACRO_TRIGGER_KEYS`, and refresh `HOTKEY_BINDINGS` from `reevaluate_all_macros` so it stays current on every trigger_key mutation and independent of engine state.

Cross-platform correction: the 09-VERIFICATION.md premise "Windows is unaffected — uses only MACRO_TRIGGER_KEYS" is contradicted by source. Windows populates AND checks both registries the same way (state/mod.rs:588-591, windows/mod.rs:524-553), so Windows carries the identical latent defect. The consolidation is applied symmetrically to both platforms.

Purpose: restore the phase Core Value ("a macro that was set up must fire reliably when triggered") for hotkey-triggered macros on macOS, and pre-empt the same defect surfacing on the first real Windows device test.
Output: single-registry hotkey dispatch on both platforms + a data-level regression unit test + a carried-forward on-device manual confirmation (T9.8).
</objective>

<decision_rationale>
Both `HOTKEY_BINDINGS` and `MACRO_TRIGGER_KEYS` are populated on BOTH platforms today, and both are consulted in each platform's keydown handler with no de-duplication — that is the root of CR-01. Traced call graph:

- `HOTKEY_BINDINGS` (macOS `Vec<HotkeyBinding>` observer.rs:59 / Windows `Vec<WindowsHotkeyBinding>` windows/mod.rs:434): action-typed (`HotkeyAction::ToggleMacro` / `ToggleEngine`), built by `build_hotkey_bindings_vec` and pushed via `update_hotkey_bindings` from the Phase-8 UX-11/UX-14 bind path (`Intent::BindHotkey`/`UnbindHotkey`, state/mod.rs:583-591, 607-615). Refreshed only on bind/unbind, but unconditionally (engine-state-independent).
- `MACRO_TRIGGER_KEYS` (anonymous `HashMap<(u16,u64), Uuid>` observer.rs:200 / windows/mod.rs:429): populated only as a side effect of `reevaluate_all_macros` (state/mod.rs:786-789), which is called by every trigger_key-mutating handler (AddMacro:469, SetMacroTriggerKey:536, BindHotkey:592, UnbindHotkey:616, LoadProfile:727, RemoveMacro:505) — comprehensive coverage, but engine-gated (reevaluate early-returns when the engine is off, state/mod.rs:756-758).

Chosen source of truth = `HOTKEY_BINDINGS`, because: (1) it is the richer, action-typed registry that also represents the `ToggleEngine` action; (2) it is the registry the ipc doc comment (ipc/mod.rs:141) already designates as macOS's observer path; (3) comprehensive refresh is a property of *where the refresh call lives*, not of the registry — moving the `HOTKEY_BINDINGS` refresh into `reevaluate_all_macros` gives it the exact comprehensive, all-paths coverage `MACRO_TRIGGER_KEYS` had, plus the engine-state-independence `HOTKEY_BINDINGS` already had.

Blast-radius / cross-platform check performed before deciding: no test references either registry (grep confirmed); `MACRO_TRIGGER_KEYS` has no consumer other than its own keydown lookup on either platform; removing it needs zero new population calls. The only capability nominally removed is `HotkeyAction::ToggleEngine` — which is currently DEAD (`build_hotkey_bindings_vec` only ever emits `ToggleMacro`; `add_hotkey_binding`, the only other populator, has zero call sites; the engine is toggled via the `toggle_engine` IPC command, not a global hotkey). `HotkeyAction`/`HOTKEY_BINDINGS` are retained intact, so even that latent variant is preserved. No user-facing feature is lost — the per-macro configurable-hotkey toggle keeps identical behavior via `HOTKEY_BINDINGS`.

Reversibility: reversible. The choice of which registry to keep is a pure code change with no data migration or external side effect; it can be swapped via git if a future need arises.

Explicitly OUT of scope (carried forward from 09-VERIFICATION.md, not this round's targets): ROADMAP SC1/SC2 real-device concurrent-firing (human_needed); Windows device tests 6.1-6.3 (blocked_by physical-device, user accepted "pass for now"); the dormant `SchedulerIntent::UpdateInterval`/`running_configs` cache item; and the `App.tsx:574-577` unbind-before-confirm ordering (CR-04). None are touched here.
</decision_rationale>

## Trust Boundaries

|----------|-------------|

| StateActor AppState -> platform static registry | Registry is written only from StateActor's owned state via the Intent channel; there is no external write path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Tampering | global hotkey registry (HOTKEY_BINDINGS static) | low | accept | Process-local, populated only from StateActor's owned AppState via the Intent channel. This change reduces surface by deleting a second redundant global registry. |
| T-09-02 | Denial of Service | keydown callback dispatch path | low | mitigate | Removing the duplicate registry lookup halves per-keypress dispatch work and eliminates the self-cancelling double Intent send; the retained `try_send` stays non-blocking (existing backpressure invariant). |
| T-09-SC | Tampering | package installs | n/a | accept | No package-manager installs in this plan — std-only (`std::collections`, existing platform crates). No `## Package Legitimacy Audit` required; no install/legitimacy checkpoint. |
