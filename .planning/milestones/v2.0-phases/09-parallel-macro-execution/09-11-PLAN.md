<objective>
Close the two confirmed Blocker-severity gaps from 09-VERIFICATION.md (score 12/16) that undermine the phase's EXEC-01/EXEC-02 reliability guarantee and the project Core Value ("a macro that was set up must fire reliably"). Both were independently re-confirmed by direct source read in the verification report.

- **Gap 1 — stuck-input:** `StateActor::handle_action` (state/mod.rs:373-413) applies Gate 1 (engine active) / Gate 2 (macro enabled+exists) / Gate 3 (target-app match) uniformly to `ActionType::HoldRelease`. Four real trigger paths (disable a Hold-mode macro, toggle engine off, switch active app away from target, load a new profile) each mutate the gating state BEFORE the guaranteed-delivery release arrives, so the release is silently discarded and the physical input stays down. Add an unconditional release bypass.
- **Gap 2 — hotkey rebind data loss:** On macOS, `handleCardSetTriggerKey` (App.tsx:572-601) calls `unbind_hotkey` unconditionally before `bind_hotkey`, so a conflict-rejected rebind ends with no binding at all. On Windows, `Intent::SetMacroTriggerKey` (state/mod.rs:514-541) silently coerces a conflicting key to None/0 with no Result reply, so `ipc::set_macro_trigger_key` always returns Ok(()) — zero user feedback. Preserve the old binding on rejection and surface the conflict.

Purpose: A Hold-mode macro's held input is always released when it stops, and the card-edit hotkey rebind flow can never silently strand a macro with no working trigger.
Output: 2 backend regression tests + 1 frontend sequencing fix; `cargo test --lib` green at 16 tests; `npx tsc --noEmit` clean.
