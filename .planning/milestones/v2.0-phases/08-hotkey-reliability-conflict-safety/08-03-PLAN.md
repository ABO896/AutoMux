Introduce the new `Intent::BindHotkey` and `Intent::UnbindHotkey` variants with oneshot-sender replies, route the `bind_hotkey` and `unbind_hotkey` IPC commands through the StateManager (eliminating the macOS-only bypass), add a Windows `HOTKEY_BINDINGS` registry + modifier-bit synthesis in `hook_callback`, and unify the two-registry design (per RESEARCH.md D-7, D-8).

It also closes the "no configurable hotkeys on Windows" gap documented in `.planning/codebase/CONCERNS.md:150-152`. The frontend surfaces for UX-11 (toast) and UX-14 (first-run banner) come in Plans 08-05 / 08-04.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend → IPC `bind_hotkey` | Untrusted JS sends a `(macro_id, keycode, modifiers)` tuple; the StateActor validates and runs the conflict check |
| StateActor → Platform `HOTKEY_BINDINGS` (macOS + Windows) | The StateActor is the source of truth; the platform statics are write-only mirrors |
| Windows `hook_callback` → Intent::ToggleMacroHotkey | The hook synthesizes a `u64` mod mask and looks up two maps; both maps must use the same bit layout for matching to work |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|----------------|
| T-08-13 | Tampering | `bind_hotkey` IPC with conflicting `(keycode, modifiers)` | mitigate | The new `Intent::BindHotkey` handler in `state/mod.rs` (Task 1) calls `check_trigger_key_conflict` and returns `Err(msg)` via the oneshot. The frontend displays the error as `ConflictErrorToast` (Plan 08-05). |
| T-08-14 | Elevation of Privilege | `bind_hotkey` on Windows with no permission gate | accept | The Windows `bind_hotkey` IPC requires the `WH_KEYBOARD_LL` hook to be installed, which itself requires the `lowlevel` token capability that is implicitly granted to standard user processes via `SetWindowsHookExW`. No additional security boundary is crossed. |
| T-08-15 | Spoofing | `build_mod_mask` reads the wrong VK_* constant | mitigate | Plan 08-01 Task 2 added a unit test that asserts the literal bit values 0x0001/0x0002/0x0004/0x0008. The `build_mod_mask` uses those exact bits; any drift would fail the test on a Windows runner. |
| T-08-16 | Denial of Service | `update_hotkey_bindings` replaces the entire Vec on every bind | accept | For typical configs (<10 macros) the operation is microseconds. The replace is necessary to keep the registry consistent with the StateActor's view. |
| T-08-17 | Repudiation | `Intent::UnbindHotkey` cannot fail | accept | By design — the absence of a binding is a no-op. The frontend gets `Ok(())` and clears its local UI state. |
| T-08-18 | Information Disclosure | Conflict error message reveals other macro's name | accept | By design per UX-11 — the user must know which macro to unbind. The message is shown only to the originating frontend, which already has access to all macro names. |

The emergency-stop flush pattern from SAFE-04 (drain into a local Vec before posting events) is already applied to the held-inputs mutex; the `HOTKEY_BINDINGS` mutex does not post events so the deadlock vector doesn't apply. |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No new dependencies in this phase. slopcheck gate not relevant. |
