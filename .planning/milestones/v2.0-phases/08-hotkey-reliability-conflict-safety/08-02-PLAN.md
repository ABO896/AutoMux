<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IPC → StateActor (Intent::AddMacro / SetMacroTriggerKey / LoadProfile) | The frontend sends a config that may claim a `trigger_key` already held by another macro; the StateActor must reject or silently coerce |
| StateActor → Derived `AppState.conflicts` | The derived field is recomputed from `macros`; a stale `conflicts` could lie to the user (UX-12) |
| Persisted profile JSON → StateActor (LoadProfile) | A loaded profile may contain macros whose enabled flags create overlap with existing macros; the recompute must run after load |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|----------------|
| T-08-07 | Tampering | `Intent::AddMacro` with conflicting `trigger_key` | mitigate | `check_trigger_key_conflict` runs before insert; on conflict the trigger is dropped (this plan) and the new `Intent::BindHotkey` reply channel (08-03) surfaces the explicit error to the frontend. The drop-on-conflict path is acceptable because the user can re-create the macro and explicitly pick a different key. |
| T-08-08 | Tampering | `Intent::SetMacroTriggerKey` with conflicting key | mitigate | Same as T-08-07. Plan 08-03's `bind_hotkey` IPC will be the user-facing path; this IPC is the "set trigger" path used by the in-card chip. |
| T-08-09 | Information Disclosure | Conflict message reveals other macro's name | accept | The frontend `ConflictErrorToast` (Plan 08-05) displays the conflicting macro's name to the user. This is by design (UX-11 requires the user to know which macro to unbind). No security boundary crossed. |
| T-08-10 | Denial of Service | `recompute_conflicts` O(n × steps) on every intent | accept | The 1000-macro stress test (persistence.rs:259) shows 5 steps × 1000 macros = 5000 hash lookups per recompute. At 10 intents/second worst case, this is 50K hash ops/sec — negligible. Documented in RESEARCH.md §3.2. |
| T-08-11 | Elevation of Privilege | `Intent::RemoveMacro` does not recheck ownership | accept | `RemoveMacro` accepts a `Uuid`; the IPC layer is the only caller, and Tauri's CSP prevents unauthorized invokes. The StateActor's role is data validation, not authorization. |
| T-08-12 | Repudiation | Silent drop of trigger_key on conflict | accept (interim) | The drop-on-conflict path for `AddMacro` / `SetMacroTriggerKey` is a stopgap until Plan 08-03's `Intent::BindHotkey` reply channel ships the explicit error. Once both paths are live (08-03), the silent drop remains as a defense-in-depth for callers that don't check the reply. |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No new dependencies in this phase. slopcheck gate not relevant. |
</threat_model>
