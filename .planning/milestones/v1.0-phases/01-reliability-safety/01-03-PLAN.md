<objective>
Deliver the Windows half of Phase 1's platform reliability slice: eliminate the 4 panicking `lock().unwrap()` calls on the Windows injection hot path (SAFE-01 sites 2–5 of 5) AND make the Ctrl+Shift+Q emergency stop synchronously flush all held inputs before exit so no keys remain stuck (RELY-03).

Purpose: Today, a poisoned mutex on the Windows hot path crashes the entire process during macro execution; and the emergency stop dispatches a non-blocking `try_send(TriggerEmergencyStop)` immediately followed by `process::exit(1)`, racing the StateActor flush — keys remain physically held down after exit. Both fixes live entirely in a single file; both deliver user-visible reliability for Windows users.

Output: All four `get_held_inputs().lock().unwrap()` sites in the `InputProvider` impl converted to `let Ok(...) else { return; }`; the `hook_callback` emergency-stop branch calls `WindowsInputProvider::flush_all_held_inputs()` synchronously before `process::exit(1)`, matching the macOS inline-flush approach.
</objective>

## Phase Goal

**As a** Windows AutoMux user, **I want to** press the emergency-stop hotkey and have every held key release immediately, and I never want a transient lock failure to crash the app, **so that** I can trust the emergency stop to leave my keyboard in a clean state and a stray mutex panic cannot terminate a running session.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Win32 hook thread → app state | Hook callback runs on a thread owned by the OS message pump; mutex contention or poisoning across this boundary must not panic |
| User keyboard → emergency stop | The user-issued emergency hotkey must produce a clean OS-level state on exit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Denial of Service | WindowsInputProvider injection hot path | mitigate | SAFE-01: replace the 4 `get_held_inputs().lock().unwrap()` sites with `let Ok(...) else { return; }` so a poisoned mutex or contention failure drops one action instead of panicking the process; per Pitfall 3, do NOT use `.into_inner()` to recover from poison |
| T-01-07 | Tampering (physical input state) | Windows emergency-stop branch | mitigate | RELY-03: call `WindowsInputProvider::flush_all_held_inputs()` synchronously between the `try_send(TriggerEmergencyStop)` and `process::exit(1)` calls so no held key or mouse button remains active on the OS after the process exits |
| T-01-08 | Repudiation | Emergency-stop best-effort flush | accept | Per D-10, the flush is best-effort; if an individual `send_key_event` fails, the loop continues and exit proceeds. This is the same semantics as macOS inline flush; no audit trail beyond the existing `println!("EMERGENCY STOP TRIGGERED")` is required. |
</threat_model>
