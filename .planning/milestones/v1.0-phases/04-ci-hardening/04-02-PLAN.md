## Phase Goal

**As a** macOS user installing AutoMux from a GitHub release,
**I want to** receive a universal binary that runs natively on both Apple Silicon and Intel hardware,
**so that** the app works without Rosetta on any supported Mac and a CI regression to arm64-only artifacts is caught before publication.

<objective>
Make the macOS release leg produce a true universal binary (arm64 + x86_64) by passing `--target universal-apple-darwin` to tauri-action via the existing platform-conditional ternary pattern (D-01, D-02), and add a blocking `lipo` verification step that fails the workflow if either architecture slice is missing from the built binary (D-03).

Purpose: Closes CI-01. The current workflow installs both Rust targets but never tells tauri-action to build for both — it silently produces an arm64-only artifact because that is the runner's native arch. The verification step makes any future regression to a single-arch build immediately visible.

Output: Modified `.github/workflows/release.yml` with (a) an `args:` field on the tauri-action step using the platform-conditional ternary, and (b) a new "Verify universal binary" step gated to the macOS leg that asserts both slices are present in the built binary.
</objective>

    Step shape (insert as the final step in the steps: list):

    - Name: `Verify universal binary`
    - Conditional: `if: matrix.platform == 'macos-latest'`
    - Body: a `run: |` multi-line shell script that:
      1. Uses `find src-tauri/target/universal-apple-darwin/release/bundle -name "AutoMux" -type f | head -1` to locate the built binary, assigning to a shell variable `BINARY`.
      2. Echoes `Checking binary: $BINARY` so the CI log shows which file was tested.
      3. Runs `lipo -archs "$BINARY"` (the unconditional output line — gives the human reader the full architecture list in the log).
      4. Runs `lipo -archs "$BINARY" | grep -q "x86_64" && lipo -archs "$BINARY" | grep -q "arm64"` — this is the BLOCKING assertion. If either grep returns 1, the chained `&&` short-circuits and the step exits non-zero, failing the workflow.
      5. Add `set -e` at the top of the run block so any earlier failure (e.g., find returning no results, lipo failing on a missing file) also fails the step instead of silently continuing.
      6. Add an explicit guard: if `BINARY` is empty after the find (no .app produced), echo a clear error message and `exit 1` — this catches the "build succeeded but bundle structure changed" case before the misleading `lipo: can't figure out the architecture type` error.

    Indentation rules (must match existing steps):
    - `- name:` line: 6 spaces
    - `if:` line: 8 spaces
    - `run: |` line: 8 spaces
    - Body lines under `run: |`: 10 spaces

    Why `lipo -archs` and not `lipo -info`: `-archs` returns a space-separated list (e.g., `x86_64 arm64`) which is reliable for `grep -q`. `-info` includes prose like "Non-fat file:" prefix that can produce false positives. PATTERNS.md explicitly mandates `-archs`.

    Out-of-scope guard (do NOT modify):
    - Any prior step (Checkout, Setup Node.js, Install Frontend Dependencies, Setup Rust, Build and Release Tauri App).
    - The Plan 01 SHA pins.
    - The Task 1 `args:` ternary.
    - Matrix, permissions, on, runs-on.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build artifact → end user | A macOS user installing the release expects a universal binary; receiving an arm64-only artifact silently breaks Intel Mac users. The lipo verification step is the gate that prevents this misrepresentation. |
| CI build environment → released artifact | tauri-action runs `cargo build` with whatever target is configured. A missing `--target` flag silently picks the runner's native arch — a tampering / misconfiguration channel that produces wrong but plausible artifacts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Tampering | tauri-action build invocation (missing --target) | mitigate | Task 1 adds the explicit `--target universal-apple-darwin` arg via platform-conditional ternary, making the build target a workflow-controlled value rather than an implicit runner-arch default. |
| T-04-07 | Information Disclosure / Integrity | Released macOS artifact silently arm64-only | mitigate | Task 2 adds blocking `lipo -archs` assertion. A regression in tauri-action behaviour, an upstream change to the bundle layout, or a future refactor that drops the `--target` arg will be caught at CI time and fail the release before publication. |
| T-04-08 | Denial of Service | Verification step false-positive failing valid builds | accept | The grep-q assertion uses fixed architecture strings that lipo emits unconditionally for fat binaries. False positives require a lipo behaviour change, which is extremely unlikely. The `set -e` and empty-binary guard prevent false NEGATIVES (e.g., find returning no results), which is the more serious risk for this feature. |
| T-04-09 | Repudiation | Build succeeds but bundle path layout changes upstream | mitigate | Empty-binary guard in Task 2 (`BINARY=$(find ...); if [ -z "$BINARY" ]; then exit 1; fi`) emits a distinct error message rather than failing silently inside `lipo`. CI log clearly indicates "binary not found at expected path" so the maintainer knows to update the find pattern. |
| T-04-10 | Elevation of Privilege | New `run:` step executing arbitrary shell on CI runner | accept | The run block executes only `find`, `echo`, `lipo`, and `grep` against paths inside the workflow's own checkout / build output. No network access, no external inputs. Runner already has access to the build output (it produced it). |
</threat_model>
