## Integration Findings

### ⚠ RELY-01: check_accessibility polling does not arm CGEventTap on external grant

The 3-second polling path in `App.tsx` (lines 161-168) calls `invoke("check_accessibility")` which returns the boolean permission state. When `true` is returned, the UI banner clears — but the `ipc::check_accessibility` handler does not call `initialize_tap()`.

**Consequence:** If a user grants Accessibility permission directly in System Settings (without clicking AutoMux's "Request Access" button), the polling detects the grant and the banner clears, but the CGEventTap is never armed. Hotkeys remain inert until the app is restarted.

**Unaffected path:** The button-click path (`handleRequestAccess` → `invoke("request_accessibility")`) calls `initialize_tap()` after opening System Settings — this path works correctly and satisfies the primary UX flow.

**Classification:** WARNING (primary UX flow works; edge case where user bypasses the button is broken).

**Affects:** RELY-01

---

### ⚠ auto-save-error Tauri event not consumed by frontend

`StateActor` emits `"auto-save-error"` with the error string when `auto_save_default()` fails (`state/mod.rs` lines 427, 499). `App.tsx` listens only for `"state-changed"` (line 150). The error event fires into a void.

**Consequence:** When disk writes fail (full disk, permissions, etc.), the user gets no feedback. The macro changes are lost without warning.

**Classification:** WARNING (auto-save fires correctly; only the failure-signal feedback loop is broken).

**Affects:** RELY-04

## Tech Debt Summary

### Phase 1: Reliability & Safety

| ID | Severity | Description |
|----|----------|-------------|
| CR-01 | Critical | `flush_held_inputs` holds registry lock while posting CGEvents — callback re-acquires same non-reentrant `REGISTRY` mutex → deadlock on macOS emergency stop |
| CR-02 | Critical | `HoldRelease` events from Scheduler dropped via `try_send` if `action_tx` is full during emergency stop — OS keys/buttons may remain held |
| CR-03 | Critical | CGEventTap TOCTOU race: if `CFRunLoop` source creation fails after `OnceLock` is set, `TAP_INITIALIZED` is never reset — zombie tap, hotkeys permanently broken |
| WR-01 | Warning | `Intent::ToggleMacroHotkey` missing `auto_save_default()` call — hotkey-toggled enabled state lost on restart |
| WR-02 | Warning | `Intent::LoadProfile` causes double `state-changed` event (explicit broadcast + run() loop unconditional broadcast) |
| WR-03 | Warning | `reevaluate_all_macros` sends `StartMacro` for all enabled macros on every state mutation — transient key-up/down for SustainedHold macros on app-switch |
| WR-04 | Warning | `auto-save-error` event emitted by backend, not consumed by frontend (see Integration section) |
