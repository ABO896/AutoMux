## process-picker-doesnt-select-clicked-app — target-app `<select>` assigns a different app than the one clicked
- **Date:** 2026-08-04
- **Error patterns:** wrong app selected, clicking dropdown option selects different item, native select mutated while open, process picker, target-app select, dropdown option desync, stuck on Loading, only Global no-target shown after fix attempt, SolidJS For reference diffing, reconcile signal never updates, createSignal reference equality
- **Root cause(s):** The target-app `<select>`'s `onFocus` handler (`handlePickerFocus`) unconditionally re-fetches the running-app list and calls `setApps()` with a brand-new array of freshly-deserialized objects on every open of the picker. SolidJS's `<For>` diffs list items by object reference (not by `app.identifier`), so every `<option>` DOM node is destroyed and rebuilt on every focus even when the app set is unchanged. The IPC round trip resolves in single-digit-to-low-double-digit milliseconds — far faster than a human's dropdown-open-to-click reaction time — so this DOM-destroying mutation reliably lands while the native `<select>` popup is still open, corrupting the click-to-value mapping the browser resolves against.
- **Fix:** Replaced the unconditional `setApps(result)` in `handlePickerFocus` with a hand-rolled reference-preserving merge: build a `Map` of the current `apps()` array keyed by `identifier`, map the freshly-fetched result to reuse each existing app's OLD object reference when `identifier` + `display_name` are unchanged (new object otherwise), and always call `setApps()` with a freshly-allocated top-level array. New top-level array reference -> plain `createSignal`'s default reference-equality check always notifies observers (reactivity preserved); unchanged per-item references -> `<For>`'s own reference-equality diffing (`mapArray`) skips rebuilding those `<option>` nodes (no DOM churn while the native dropdown may be open). NOTE: an earlier fix attempt in this same session wrapped `result` in solid-js's `reconcile(result, { key: "identifier" })` before calling `setApps()` — this is a `createStore`-oriented primitive; applied to a plain `createSignal` it mutates the previous array in place and returns the SAME reference every call, which the signal's default `===` equality check reads as "no change," permanently freezing `<For>` at its initial empty render (regression: stuck on "Loading…", then only "Global (no target)" ever shown). That attempt was reverted before the fix above was applied.
- **Files changed:** src/App.tsx (handlePickerFocus, App.tsx:734-768 after fix — replaced direct `setApps(result)` with the Map-based reference-preserving merge; no `solid-js/store` import was retained)
- **Why not caught:** No gate existed for this class. This repo has no frontend test framework (confirmed via TECH-STACK docs: "No frontend test framework detected"), so neither the original defect (focus-triggered refetch feeding a reference-diffing `<For>`) nor the regression introduced by the first fix attempt (`reconcile()` misapplied to a plain `createSignal`, which silently breaks all reactivity for that signal) had any automated check — unit, type, or lint — capable of catching them. TypeScript's type checker does not catch this class: both the buggy and fixed code are fully type-correct: the defect is a runtime reactivity/rendering-timing behavior, not a type error. Code review (human or automated) is the only gate that exists for `src/App.tsx`, and it did not catch either issue when they were originally introduced.
- **Recurrence guard:** (1) An inline code comment was committed directly at the fix site (`src/App.tsx`, `handlePickerFocus`) documenting both failure modes by name — the `<For>`-reference-diffing-plus-focus-refetch defect and the `reconcile()`-on-plain-`createSignal` anti-pattern — so a future contributor or reviewer touching this function sees the documented mechanism before reintroducing either one. (2) This knowledge-base entry itself: a future Phase-0 semantic/keyword recall will surface it for any symptom resembling "dropdown/select picks the wrong option," "SolidJS signal won't update," or "stuck on Loading," short-circuiting re-diagnosis of an already-solved failure mode. No regression test exists (no test framework available) and no lint rule was added — this repo has no ESLint config wired for reactive-primitive misuse detection, so the comment + KB entry are the strongest guards currently achievable without introducing new tooling.
