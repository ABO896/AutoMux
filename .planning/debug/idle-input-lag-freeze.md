# Debug Session: idle-input-lag-freeze

## Symptoms

- **expected**: Per requirement UI-04 ("UI redesign must not increase idle memory/CPU overhead — keep AutoMux lightweight"), AutoMux sitting open and fully idle (no macro enabled/running) should have negligible effect on system responsiveness — this is the exact property the pending 10-VERIFICATION.md checklist item 5 ("UI-04 perf check: idle CPU/GPU with the app open and no macro running is not measurably higher than the v1.2.0 baseline") is meant to confirm before Phase 10 can close.
- **actual**: Within 1-3 minutes of launching AutoMux — fully idle, no macro created/enabled, nothing actively firing — system-wide mouse input became severely laggy: clicks took seconds to register anywhere on the system (not just inside the AutoMux window). User closed AutoMux; for a few seconds afterward the cursor rendered abnormally large, then the system fully stabilized and returned to normal responsiveness on its own (no forced reboot needed for the incident itself).
- **error**: None observed/captured by the user — no visible crash dialog, no console error surfaced. Purely an input-latency + cursor-rendering symptom. Investigator note: `last reboot` shows the Mac rebooted ~4 minutes before this debug session started; no AutoMux entry exists in `~/Library/Logs/DiagnosticReports/` or `/Library/Logs/DiagnosticReports/` for today, and no kernel panic report was found either — so that reboot is NOT confirmed to be caused by this incident (could be an unrelated/deliberate restart) and should not be assumed as evidence of a harder crash than what the user directly described.
- **timeline**: First noticed today (2026-07-27), during the still-open Phase 10 checkpoint (see 10-VERIFICATION.md, Round 2 awaiting re-confirmation of the glass-blur fix). Not yet established whether this is a new regression from recent uncommitted/recent CSS changes (commit `1b79ed6` added `-webkit-backdrop-filter` + ambient `radial-gradient` to `src/App.css`; a follow-up geometry widening of those gradients was just applied and is uncommitted per `git status` — see `.planning/debug/glass-blur-still-not-visible.md`) or a pre-existing latent issue in the Rust backend (CGEventTap observer, Scheduler timers, StateActor) that simply hadn't been noticed until the human started deliberately watching for idle overhead as part of this checkpoint.
- **reproduction**: Launch AutoMux, leave it fully idle for 1-3 minutes (no macro created or enabled, nothing triggered), then try to click/interact anywhere on the system — observe multi-second input latency system-wide.

## Context for investigation

- Relevant recent/uncommitted change: `src/App.css` — `-webkit-backdrop-filter: blur(20px) saturate(1.5)` on `.glass-card` / `.sidebar-glass`, plus two `radial-gradient` blobs with `background-attachment: fixed` on `body`. `backdrop-filter` is a known WKWebView compositor cost; worth checking whether it compounds/leaks over time (e.g. repeated re-composite triggered by something animating or re-rendering even while idle) — see also community reports of Tauri/wry WKWebView backdrop-filter weirdness referenced in `.planning/debug/glass-blur-still-not-visible.md`.
- Relevant backend surfaces per architecture (`CLAUDE.md`): the macOS `CGEventTap` observer (`src-tauri/src/platform/macos/observer.rs`) runs on its own OS thread and is the only thing that taps *all* system input events — a slow/blocking callback here is the classic root cause of exactly this symptom (macOS throttles/disables event delivery system-wide when a tap's callback is slow, which presents as universal input lag, not just lag inside the app). A previous distinct (already-resolved) bug in this same file caused a PAC-related crash when `CGEventTapEnable` was called from inside the tap callback (`.planning/debug/cgeventtap-pac-crash-macos26.md`) — different trigger (only fired when a macro was triggered) and different symptom (hard crash, not system-wide lag), but the same file/subsystem is worth re-examining for any code path that could block or loop inside the tap callback even with zero macros configured.
- Also worth checking: `Scheduler` timer loop (`src-tauri/src/scheduler/mod.rs`) and `StateActor` (`src-tauri/src/state/mod.rs`) for any polling/interval work that runs regardless of whether a macro is enabled, and the static `OnceLock` registries in `observer.rs` (`STATE_TX`, `TAP_INITIALIZED`, `REGISTRY`, `ACTIVE_APP`, `HOTKEY_BINDINGS`) for lock contention — `CLAUDE.md` already flags "SAFE-04: Lock ordering fix (release REGISTRY before CGEvent dispatch) is subtle — requires careful audit" as a known-delicate area.
- AutoMux is NOT currently running (confirmed via `ps aux`), so live process inspection will require relaunching it (e.g. `npm run tauri dev`) to reproduce and observe.

## Resolution

root_cause: "check_accessibility_permissions(false) and check_input_monitoring() (src-tauri/src/platform/macos/mod.rs) each construct a `core_graphics::event::CGEventTap` (HID location, ListenOnly, MouseMoved) purely as a proxy to test whether this process currently holds Accessibility/Input-Monitoring trust — a deliberate replacement for the stale-caching AXIsProcessTrusted() (commit 403c8ba, Phase 06-01). Neither function ever calls CFMachPortInvalidate() on the probe's underlying Mach port before it falls out of scope. core-graphics 0.24.0's CGEventTap/CFMachPort has no Drop impl beyond the default core-foundation CFRelease (confirmed via direct source read of event.rs:471-517 and mach_port.rs) — CFRelease alone does not unregister a CGEventTapCreate-derived tap with the WindowServer; CFMachPortInvalidate() must be called explicitly, or the registration persists until the OWNING PROCESS EXITS (confirmed via Apple Developer Forums documentation of the required CGEventTap teardown sequence). src/App.tsx's unconditional 3-second poll effect (added Phase 07-03, commit 6b9ab2c) calls both check_accessibility and check_input_monitoring together, forever, for the entire time AutoMux is open — regardless of macro/engine state. This leaks ~2 live, system-wide-registered HID event taps every 3 seconds (~40/minute), degrading the WindowServer's shared input-dispatch path for the ENTIRE system (not just AutoMux's own window), matching the reported 1-3 minute onset of universal multi-second click latency. Quitting AutoMux causes the OS to reclaim all its Mach ports/tap registrations at once, explaining full system recovery (plus the transient oversized-cursor WindowServer glitch) shortly after close. This is a PRE-EXISTING latent bug (present since v1.0.0-rc / Phase 06-07), unrelated to the recent/uncommitted Phase 10 backdrop-filter CSS changes — it was never noticed before because no test suite exercises multi-minute idle duration, and nobody had specifically watched for idle degradation over that timescale until the Phase 10 UI-04 checklist item forced exactly that kind of observation."
fix: "In src-tauri/src/platform/macos/mod.rs: added an explicit `core_foundation_sys::mach_port::CFMachPortInvalidate(tap.mach_port.as_concrete_TypeRef())` call (via `core_foundation::base::TCFType`) to both check_accessibility_permissions's silent-check branch and check_input_monitoring, immediately after `probe.is_ok()` is captured and before the probe falls out of scope. No polling frequency, permission-check logic, or UI behavior was changed — this is the minimal addition of the documented-required teardown call for a CGEventTapCreate-derived Mach port. Added a regression test (probe_event_tap_invalidate_prevents_leak) mirroring the exact tap-creation pattern and asserting CFMachPortIsValid transitions from valid (1) to invalid (0) after CFMachPortInvalidate — this is the assertion meant to catch any future regression of either call site's invalidate call."
verification: "cargo build: clean, zero warnings. cargo test: 25/25 pass (24 pre-existing + 1 new regression test), zero regressions. RED/GREEN proof performed directly on the new regression test: temporarily removed its CFMachPortInvalidate call -> test FAILED with the exact expected 'BUG REGRESSION (idle-input-lag-freeze)' assertion message (left=1 valid, right=0 expected) -> restored -> test PASSED again. This test process is Accessibility-trusted in this environment, so the assertions genuinely executed (not skipped) — CFMachPortIsValid measurably transitioned from 1 to 0 upon CFMachPortInvalidate, empirically confirming the fix's mechanism using the real macOS API, not just source-reading inference.
