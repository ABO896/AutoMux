# Debug Session: glass-blur-still-not-visible

## Symptoms

- **expected**: `.glass-card` and `.sidebar-glass` show a visible frosted-glass/translucency effect — content behind the panel should appear blurred, per UI-SPEC checklist item 4.
- **actual**: App window (screenshot, dark theme, live `tauri dev` build on macOS Tahoe) shows a completely flat, uniform dark background behind both the sidebar and the content cards — no blur, no visible gradient, no translucency of any kind. User confirms both light and dark themes "look good" stylistically (item 3 passes) but item 4 still fails identically to Round 1.
- **error**: None — no console error, no crash. Purely a visual/rendering absence.
- **timeline**: Round 1 checklist (2026-07-24/25) found item 4 failing with a flat background. Root cause was diagnosed as (a) missing `-webkit-backdrop-filter` (WKWebView needs the prefixed property) and (b) a perfectly flat `body` background giving `backdrop-filter: blur()` nothing to blur. Fix applied in commit `1b79ed6`: added `-webkit-backdrop-filter` to both selectors, plus two low-opacity `radial-gradient` blobs on `body` using `color-mix(in srgb, var(--color-accent) N%, transparent)` with `background-attachment: fixed`. `npx tsc --noEmit` and `cargo build` both reconfirmed clean after the fix. This session (Round 2) re-tested on the same live `tauri dev` build and the effect is STILL not visible — the fix in 1b79ed6 did not resolve the symptom.
- **reproduction**: Run `npm run tauri dev`, look at the sidebar and macro-list card region in either theme. No blur/gradient/transparency visible anywhere.
- **context**:
  - Device: macOS Tahoe 26, Tauri 2 (WKWebView-based webview)
  - Build: live `npm run tauri dev` (not a release bundle)
  - File: `src/App.css` — `.glass-card`, `.sidebar-glass` classes
  - Relevant commits: `1b79ed6` (Round 1 fix, apparently ineffective), `4be5acb` (docs recording Round 1 result)
  - Screenshot confirms: solid near-black background, no radial-gradient blobs visible, no blur on sidebar/card edges despite the fix being in `src/App.css`

## Resolution

root_cause: "Round 1's fix (commit 1b79ed6) correctly added -webkit-backdrop-filter and translucent color-mix backgrounds, and correctly added ambient radial-gradient blobs to body so backdrop-filter would have something to blur — but the blobs were positioned tight to opposite corners (12%/18% and 88%/82%) with a short falloff (transparent at 42%/48% of farthest-corner distance). This left the window's geometric center — and the content pane where most .glass-card elements actually render — with only ~1.6-2.7% combined alpha (empirically measured via native Canvas2D gradient rasterization), i.e. visually indistinguishable from a flat background. The backdrop-filter/color-mix CSS mechanism itself was proven correct at every level (live getComputedStyle inspection in WebKit); the bug was purely geometric/design (insufficient gradient reach relative to actual card placement), not a rendering or cascade defect."
fix: "In src/App.css, widened both body radial-gradient transparent-stops from 42%/48% to 85%/90% of farthest-corner distance (percentage-based, scales correctly across the app's resizable window range) and raised base color-mix percentages from 16%/10% to 22%/16% to compensate for the longer falloff dilution. Repositioned blob centers slightly (12%/18%→15%/20%, 88%/82%→85%/80%) for symmetry. No changes to backdrop-filter/-webkit-backdrop-filter or the color-mix translucent background declarations themselves — those were already correct."

## Final Resolution (2026-08-04)

root_cause: "CONFIRMED (upgraded from Round 2's residual/fallback hypothesis to primary, now with direct-embedding evidence): Tauri's embedded WKWebView (via wry) does not composite `backdrop-filter` visually, despite computing every related CSS value (translucent color-mix backgrounds, backdrop-filter blur/saturate values, ambient gradient alpha/stops) exactly as authored — verified via getComputedStyle() run directly inside the real embedded webview's own DevTools console, not a proxy. This is a known class of rendering-pipeline bug in the Tauri/wry ecosystem (community-tracked: tauri-apps/tauri#13801 'Backdrop blur not behaving the same as Safari on MacOS', #2976, #2826), not a defect in this app's CSS authoring. The reliable fix for this class of bug is native OS-level window vibrancy (the `window-vibrancy` crate, calling NSVisualEffectView on macOS / DWM Mica on Windows directly at the window-compositor level, bypassing WebView CSS rendering) — but this requires a new Cargo dependency, `transparent: true` on the window (currently `false`), and platform-specific code on both macOS and Windows for parity."
decision: "User decision (2026-08-04): forego transparency/frosted-glass effects entirely rather than pursue native vibrancy. Rationale (user's words): aesthetics and 'little effects' are 'the cherry on top, not the core purpose and objective of AutoMux' (core value: reliable macro automation). This is a deliberate scope decision, not an unresolved bug — recorded in `.planning/REQUIREMENTS.md`'s Out of Scope table and reflected in UI-01/UI-03's requirement annotations."
fix: "Simplified src/App.css: removed the non-functional `-webkit-backdrop-filter`/`backdrop-filter` declarations from `.glass-card` and `.sidebar-glass` (dead code — proven never to render in this webview), and removed the ambient radial-gradient body background hack (Round 1 + Round 2 work) that existed solely to feed the non-functional blur. `.glass-card` now uses a plain opaque `var(--color-surface)` background; `.sidebar-glass` uses `var(--color-surface-alt)`. No behavioral risk — this is a pure CSS simplification removing code that was already visually inert."
verification: "npx tsc --noEmit clean (CSS-only change, no TS impact). grep confirms zero remaining backdrop-filter/backdrop-blur usage anywhere in src/. Phase 10's human-verify checklist item 4 is marked waived (not failed) in 10-VERIFICATION.md; all other 22/23 items already passed Round 1 and are unaffected by this change."
