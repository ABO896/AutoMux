<objective>
Close two independent macOS platform-observer gaps from Phase 9 UAT (09-UAT.md), both diagnosed with file:line evidence and both living in `src-tauri/src/platform/macos/observer.rs`:

- **G-09-1a (major, perf):** The CGEventTap created in `initialize_tap()` subscribes to five high-frequency event types (mouse-moved, the three per-button drag variants, and scroll-wheel) that the callback never reads. Because the tap is a ListenOnly HID-stream `HeadInsertEventTap` held for the whole app lifetime, macOS must synchronously relay every such system-wide event through this process even when no macro is active — a permanent responsiveness tax that persists after every macro is stopped. Fix: narrow the event-mask vec to only the 8 event types the callback consumes.
- **G-09-1c (major, targeting):** `AppState.active_app` is only updated by an NSWorkspace activation-notification observer registered via a raw `msg_send!` with zero failure logging and zero handler instrumentation; if it silently fails, `active_app` stays pinned to launch-time and app-scoped macros never match (Global macros bypass the check and work). Fix: instrument the handler and registration-failure branch, and read the activated bundle id directly from the notification's `userInfo` (harder-to-race than re-querying `frontmostApplication()`), optionally via the typed `addObserverForName_object_queue_usingBlock` API.

Purpose: Uphold the project Core Value — a configured macro must fire reliably and the app must not degrade the host system. G-09-1a restores baseline responsiveness; G-09-1c makes app-scoped targeting actually fire.
Output: A narrowed CGEventTap mask and a hardened+instrumented NSWorkspace active-app observer in `src-tauri/src/platform/macos/observer.rs`. No new files. No new dependencies (both `NSWorkspaceApplicationKey` and `NSRunningApplication::bundleIdentifier` already ship in the pinned `objc2-app-kit 0.3.2`).

Scope note (multi-source coverage): GOAL (Phase 9 parallel execution), REQ (EXEC-01/EXEC-02) and CONTEXT breadth are already COVERED by executed plans 09-01 through 09-06. <task type="auto">
  <name>Task 1: Narrow the CGEventTap event mask to the consumed event types (G-09-1a)</name>
  <files>src-tauri/src/platform/macos/observer.rs</files>
  <action>
In `initialize_tap()`, the `CGEventTap::new(...)` call passes an event-mask `vec![...]` (observer.rs lines 246-260) containing 13 event types. Five of them are never referenced anywhere in the callback body: the mouse-moved variant, the left/right/other mouse DRAG variants (three of them), and the scroll-wheel variant. Remove exactly those five entries, leaving the eight the callback actually reads:
  - KeyDown, KeyUp
  - LeftMouseDown, LeftMouseUp
  - RightMouseDown, RightMouseUp
  - OtherMouseDown, OtherMouseUp

Rationale (from the G-09-1a debug session): the tap is `CGEventTapOptions::ListenOnly` at `CGEventTapPlacement::HeadInsertEventTap` on the `CGEventTapLocation::HID` stream, created once for the app lifetime. Subscribing to system-wide motion/drag/scroll forces macOS to relay every such event through this process for the whole runtime, independent of macro state — the exact cause of the persistent post-stop slowdown. The LLMHF_INJECTED registry match (observer.rs:296-323) and the KeyDown-gated hotkey/emergency-stop logic (observer.rs:329+) only ever read the eight retained types, so removing the five unused variants changes NO behavior.

Constraints:
  - Do NOT alter the `TapDisabledByTimeout | TapDisabledByUserInput` handling block (observer.rs:278-290). Those are control events delivered regardless of the mask and are not part of the subscription vec.
  - Do NOT modify the compounding factors named in the debug session (input.rs HID re-post loopback; the state/mod.rs:240-241 debug eprintln) — they are out of scope for this root-cause fix.
  - Do NOT leave a comment behind that names the removed variants; if you annotate, describe the change by concept only.
  </action>

  <name>Task 2: Instrument and harden the NSWorkspace active-app observer (G-09-1c)</name>
  <files>src-tauri/src/platform/macos/observer.rs</files>
  <action>
Target `MacPlatformObserver::start_observing()` (observer.rs:526-596), specifically the `NSWorkspaceDidActivateApplicationNotification` handler closure (lines 532-549) and its registration (lines 551-572). Apply three changes:

1. Registration-failure logging (and, if feasible, a typed API). The current registration uses a raw `msg_send![&center, addObserverForName: ... usingBlock: &*handler]` followed by a manual `Retained::retain(ret)` and an `if let Some(obs) = observer { ... }` with NO else branch — a nil return is silently ignored. Add an explicit failure branch that logs:
     `eprintln!("[Observer] NSWorkspace active-app observer registration FAILED — app-scoped macros will not re-evaluate on app switch");`
   mirroring the existing WR-04 CGEventTap failure log a few lines below (observer.rs:593). Prefer replacing the raw `msg_send!` with the typed `NSNotificationCenter::addObserverForName_object_queue_usingBlock` method (available in the pinned objc2-foundation 0.3.2 — see `~/.cargo/registry/.../objc2-foundation-0.3.2/src/generated/NSNotification.rs:212`, and confirm the exact signature/return type via Context7 or that source). It returns a retained observer object directly, removing the fragile null-pointer round-trip. If the typed method's block-signature requirements prove incompatible with the existing `RcBlock` in this crate version, keep `msg_send!` but still add the logged failure branch.

2. Handler entry instrumentation. At the top of (or where the bundle id is resolved inside) the handler closure, add a debug-only log so the next dev-mode UAT empirically confirms whether the callback fires on real app switches:
     `#[cfg(debug_assertions)] eprintln!("[Observer] active-app changed -> {:?}", id_string);`

3. Read the activated app from the notification payload instead of re-querying frontmostApplication(). Inside the handler, dereference the `_notification: NonNull<NSNotification>` parameter (`let notification = unsafe { _notification.as_ref() };`), get `notification.userInfo()` (Option<Retained<NSDictionary>>), look up the key `NSWorkspaceApplicationKey` (import from `objc2_app_kit`), downcast the value to `NSRunningApplication` (import from `objc2_app_kit`), and read its `bundleIdentifier()` — this is the app that just activated, and is not subject to the re-query race that `NSWorkspace::frontmostApplication()` has. Fall back to the existing `frontmostApplication()` path only if the userInfo lookup yields None. Keep the existing "lock get_active_app_state(), set it, drop the lock, then STATE_TX.try_send(Intent::ActiveAppChanged(...))" dispatch flow unchanged — only the SOURCE of the bundle id changes.

Leave the launch-time initial snapshot block (observer.rs:574-586) using `frontmostApplication()` — there is no notification available at startup. Do NOT touch the state/mod.rs targeting comparison (it is already correct). Add imports as needed: `NSRunningApplication` and `NSWorkspaceApplicationKey` from `objc2_app_kit`; `NSDictionary`/`NSString` from `objc2_foundation`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS input stream (HID) → CGEventTap callback | The tap observes system-wide input events. This change NARROWS what the app subscribes to (removes motion/drag/scroll), reducing the app's visibility into unrelated user input — an attack-surface / privacy reduction, not an expansion. |
| macOS NSWorkspace notification → handler | The active-app identity is supplied by the OS (trusted first-party). This change reads that identity from the notification's own `userInfo` payload rather than re-querying global state. No new external/untrusted input crosses the boundary. |

No package-manager installs occur in this plan (no `Cargo.toml` change; both `NSWorkspaceApplicationKey` and `NSRunningApplication` already ship in the pinned `objc2-app-kit 0.3.2`). No `[ASSUMED]`/`[SUS]` packages, so no package-legitimacy checkpoint (`T-09-SC`) is required.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-07-01 | Information Disclosure | CGEventTap subscription mask (observer.rs) | low | mitigate | Narrowing the mask removes the app's subscription to system-wide mouse motion/drag/scroll — the app no longer receives (and thus cannot leak/log) unrelated pointer movement. Net reduction in observed data. |
| T-09-07-02 | Spoofing | active-app identity from NSWorkspace notification | low | accept | The active-app bundle id is provided by the OS's own activation notification (`NSWorkspaceApplicationKey`), a trusted source; a local process spoofing NSWorkspace notifications would already require code-execution privileges that moot the targeting gate. Reading from userInfo is no less trustworthy than the prior frontmostApplication() query. |
| T-09-07-03 | Denial of Service | permanent CGEventTap responsiveness tax (observer.rs) | medium | mitigate | The pre-fix over-broad mask degraded whole-system responsiveness for the app's lifetime (a self-inflicted DoS on the host). Narrowing the mask to consumed types removes the tax — this is the primary fix for G-09-1a. |
</threat_model>
