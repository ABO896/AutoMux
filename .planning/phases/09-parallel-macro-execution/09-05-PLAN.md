<objective>
Close the single actionable Blocker gap in 09-VERIFICATION.md (surfaced by the fresh 09-REVIEW.md pass as its CR-01): the scheduler's per-macro stop path silently drops the `HoldRelease` under action-channel saturation, which can leave a physical key/mouse button permanently held down.

`release_holds` (src-tauri/src/scheduler/mod.rs:368-391) removes the macro's holds from `active_holds` and then sends each `HoldRelease` via fire-and-forget `self.action_tx.try_send(...)`. `release_holds` is reached from `stop_macro` (345-365), which is invoked on every normal `StopMacro` intent (handle_intent arm at ~211-213) and on every CR-04 restart inside `start_macro` (~270). Under action-channel saturation — exactly the condition Phase 9's parallel execution amplifies (many concurrent interval fires filling the 1024-slot `action_tx`) — the `try_send` fails, the message is silently dropped, `active_holds.remove(macro_id)` has ALREADY run (the scheduler now believes the hold is released), and there is no retry path short of a full emergency stop. In release builds the debug-only `ACTION_DROP_COUNT`/`eprintln` give zero diagnostic signal. A user disabling one Hold-mode macro (e.g. a sustained right-click AFK-farm macro) under load can be left with that button physically down in-game with no on-screen indication. This directly threatens the project's stated Core Value: "a macro that was set up must fire reliably."

The codebase already contains the correct, hardened pattern for the identical message type on the emergency-stop path: `SchedulerIntent::StopAll` (scheduler/mod.rs:214-234) uses guaranteed `.await` delivery, with an in-file `@safety-officer` CR-02 comment (215-217) documenting that this guarantee exists precisely because a dropped `HoldRelease` means a real, physically-stuck input. The ordinary per-macro stop path never received the same hardening — it predates Phase 9 (present since v1.0, commit ccd48e6) and was a documented D-09 scope boundary (diagnostic counter only), which 09-VERIFICATION.md's own re-review re-flagged as insufficient given how much more likely saturation becomes under genuine parallel execution.

**Fix (per 09-VERIFICATION.md's `missing` list, verbatim intent):** make `stop_macro`/`release_holds` (and therefore `start_macro`, which calls `stop_macro`) `async`, and `.await` the `HoldRelease` send in `release_holds` exactly as `StopAll` already does, so delivery is guaranteed even when the channel is full. Update the two `handle_intent` call sites (StartMacro arm, StopMacro arm) to `.await`. This is a backend-only (Rust) change confined to `src-tauri/src/scheduler/mod.rs` — no frontend / src/App.tsx change, no IPC change, no new AppState field, no new dependency.

This plan deliberately supersedes D-09's original "diagnostic-only" scope for this one `release_holds` site (and only this site), which is the disposition 09-VERIFICATION.md's `human_verification` item #3 explicitly authorizes ("fix now — mirror StopAll's .await pattern"). The other two `try_send` sites (fire_due_actions Interval, start_macro HoldStart) stay exactly as D-09 scoped them — a dropped interval click self-corrects on the next tick and a dropped HoldStart never registers a hold to leak, so neither is the stuck-input class this gap is about.

Purpose: Guarantee that disabling/stopping a Hold-mode macro always releases its held input, closing the Core-Value reliability gap that parallel execution makes materially more likely.
Output: `stop_macro`/`release_holds`/`start_macro` converted to guaranteed-delivery async (mirroring StopAll), plus a saturation regression test that fails on the old fire-and-forget path and passes on the fix. Entirely within `src-tauri/src/scheduler/mod.rs`.

**Out of scope (NOT planned here):** The 6 device-level manual tests (macOS T9.1-T9.3, Windows 6.1-6.3) in 09-VERIFICATION.md §5/§6 remain pending human verification. The two non-stuck-input `try_send` sites and their D-09 debug drop counter stay as-is. No frontend, IPC, persistence, or AppState change. 09-REVIEW.md's other findings (CR-02 hotkey-rebind, WR-01..WR-04, IN-01..IN-03) are pre-existing Phase 8 / persistence / UX concerns outside this phase's scope and are not addressed here.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Scheduler task → StateActor task | The scheduler sends `ActionReady` (including `HoldRelease`) to the StateActor over the internal bounded `action_tx` channel (capacity 1024). The StateActor is the sole consumer and the only input-injection site. This plan changes the delivery guarantee on the `HoldRelease` message from best-effort (`try_send`) to guaranteed (`.await`). |
| StateActor task → Scheduler task | The StateActor sends `SchedulerIntent` (Start/Stop/StopAll/UpdateInterval) over `sched_tx` (capacity 100), including from `reevaluate_all_macros`. Relevant because the fix makes the scheduler occasionally await while holding intent processing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-05a | Tampering (input integrity) | release_holds HoldRelease delivery | high | mitigate | Root threat this plan closes: a dropped HoldRelease under `try_send` backpressure leaves a physical input held down after the scheduler has already forgotten it owns the hold (Core-Value violation). Mitigation: guaranteed `.await` delivery mirroring StopAll (CR-02), proven by the capacity-1 saturation regression test asserting hold_releases == 1. |
