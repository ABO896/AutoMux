# Phase 10 — UI Design Contract

> Visual and interaction contract for Phase 10 (UI Redesign & Macro Management). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This is a **full visual redesign** of AutoMux's single-file `App.tsx` UI, plus net-new macro edit/delete-confirmation surfaces. Unlike Phase 8 (additive-only), this phase supersedes the existing `.glass-card` gradient treatment, the current `@theme` color tokens (adds a light-mode variant), the current typography scale, and the current two-tab navigation. Everything documented here is the new source of truth; where a value is unchanged from `08-UI-SPEC.md` it is called out explicitly as "carried forward."

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Tailwind CSS 4 via `@tailwindcss/vite` + custom `@theme` tokens; SolidJS project — **shadcn is not applicable**, it targets React) |
| Preset | not applicable |
| Component library | none (no Radix, no Base UI, no Ark UI, no Kobalte — SolidJS project, zero new UI dependencies this phase) |
| Icon library | none — inline glyphs/emoji only, **same convention as Phase 8/9** (⚡ 🎯 ⌨ 🖱 ⏱ 🔒 🌐 📁 ✎ ✕ ☀ 🌙 🖥). Decision: do NOT introduce an icon font/SVG library (e.g. Lucide, Phosphor) this phase — UI-04 (no idle memory/CPU overhead increase) makes a zero-new-dependency redesign the lower-risk default, and the existing glyph vocabulary already reads clean at the sizes used. |
| Font | `Inter, ui-sans-serif, system-ui, sans-serif` — carried forward from `App.css:5`, unchanged |
| Framework surface | Tauri 2 window config (`src-tauri/tauri.conf.json`) is part of this contract — see **Window & Chrome** below |

**Why no shadcn:** project is SolidJS; shadcn targets React exclusively. The Tailwind 4 `@theme` block in `App.css` remains the design-system source of truth, extended this phase with a light-mode token set (D-06/D-07).

**Why no new component library:** AutoMux has no modals today (per CONVENTIONS.md) and this phase's two new interaction patterns — inline macro edit (D-13) and inline delete confirmation (D-14) — are both explicitly "no modal/overlay" by user decision. There is no interaction in this phase's scope (dropdowns, toggles, inline forms, sidebar nav) that requires a component library; hand-rolled Tailwind + SolidJS `Show`/`For` is sufficient and matches the existing codebase convention.

## Window & Chrome (D-04, D-08, D-09)

This phase modifies `src-tauri/tauri.conf.json` window config and introduces a persistent sidebar, replacing the current top tab bar.

| Property | Current (v1.2.0/Phase 8) | New (Phase 10) | Rationale |
|----------|---------------------------|-----------------|-----------|
| `width` / `height` | 420 × 640 | **720 × 680** | D-09 resolution: widen toward Raycast-like proportions to fit a persistent sidebar + wider macro cards (room for a two-column meta row: target app + trigger key side by side, instead of today's cramped single line). Not landscape-wide like Raycast's command-bar window (750×474) because AutoMux's content is a scrollable list, not a single-row search result — portrait-leaning is the right shape for this content. |
| `minWidth` / `minHeight` | 360 × 480 | **560 × 520** | Sidebar (84px) + minimum usable content column (≈420px, matching the old full width) plus vertical room for at least one full macro card and the sidebar's 2 nav items. |
| `decorations` | `true` | `true` (unchanged) | No native chrome change — still uses the existing custom drag-region titlebar pattern (`[data-tauri-drag-region]` in `App.css`). |
| `transparent` | `false` | **`false` (unchanged)** | **D-04 resolution: CSS-only blur, no native window vibrancy.** True OS-level vibrancy (`transparent: true` + `NSVisualEffectView` on macOS / Acrylic-Mica on Windows) requires platform-specific Rust window-chrome code on *both* platforms and risks the UI-04 no-overhead constraint (native compositing effects + two more platform code paths to maintain). CSS-only `backdrop-filter: blur(...)` (D-03) achieves the same "liquid glass" visual language with zero native surface — the app window itself stays opaque (matching `--color-background`), and translucency/blur happens only between internal panels (sidebar over content, cards over background). This is the safer default absent a strong reason to go native, per the CONTEXT.md rationale. |

**Navigation restructure (D-08 resolution):** Replace the current top tab bar (`Dashboard | Profiles`) with a **persistent left icon+label sidebar rail**, 84px wide, not collapsible. A list+detail split (the other D-08 option) is explicitly ruled out because D-13 already locks macro editing to **inline expand-in-place on the card itself** — a detail pane would have nothing distinct to show that the expanded card doesn't already provide, making a second pane redundant. The sidebar is therefore the lighter-weight structural change that still delivers a "Raycast-inspired... efficient use of space, keyboard-navigable" hierarchy (UI-02).

Sidebar contents (top to bottom):
1. Nav item: `⚡` icon + `Macros` label (maps to current Dashboard tab content)
2. Nav item: `📁` icon + `Profiles` label (maps to current Profiles tab content)
3. *(spacer, flex-grow)*
4. Theme toggle button (see **Theme Toggle** below) — bottom of the rail, mirrors Raycast/VS Code convention of settings-adjacent controls anchored at the rail's foot.

Sidebar item states: inactive = `text-text-muted` icon+label; active = `bg-accent/10` pill background, `text-accent` icon+label, no border (matches the reserved-for-accent list below); hover (inactive only) = `text-text-main`.

## Theme System (D-06, D-07)

AutoMux is dark-only today. This phase adds a light theme.

- **Default:** follows OS `prefers-color-scheme` (D-07).
- **Override:** manual toggle in the sidebar footer, **3-state cycle**: `System → Light → Dark → System …`. Current state shown via icon: `🖥` (System), `☀` (Light), `🌙` (Dark).
- **Persistence:** stored in `localStorage` key `automux.theme_preference` (values: `"system" | "light" | "dark"`), read on boot before first paint to avoid a flash of the wrong theme.
- **Mechanism:** a `data-theme="light" | "dark"` attribute on `<html>` (or `<body>`), set by a small boot-time script/effect that resolves `"system"` via `window.matchMedia("(prefers-color-scheme: dark)")` and re-resolves on that media query's `change` event while the preference is `"system"`.
- **Token scoping:** the existing `@theme` block in `App.css` becomes the dark-mode token set (unchanged values); a new `[data-theme="light"] { ... }` override block (or CSS `@theme` + `@media`/attribute selector per Tailwind 4 conventions) supplies the light-mode values below. All existing `bg-accent`, `text-text-muted`, etc. utility classes continue to work unchanged — only the underlying CSS custom property values swap.

## Translucency (D-03)

- **Mechanism:** real `backdrop-filter: blur(Npx)` (not the current gradient-only `.glass-card`, which has zero actual blur).
- **New `.glass-card` treatment:**
  - `background: color-mix(in srgb, var(--color-surface) 72%, transparent)` (translucent, not opaque) layered over `backdrop-filter: blur(20px) saturate(150%)`.
  - `border: 1px solid var(--color-border)` (unchanged pattern).
  - Sidebar gets its own translucent treatment: `background: color-mix(in srgb, var(--color-surface) 60%, transparent)` + `backdrop-filter: blur(24px)` — sits visually "above" the content column, which needs a subtly stronger blur than cards to read as a distinct layer per Raycast/macOS sidebar convention.
- **UI-04 perf gate (explicit, must be verified by the executor/checker):** `backdrop-filter` has a known GPU compositing cost. Before this phase is marked complete, measure idle CPU/GPU with the new blur active (Activity Monitor / Task Manager, app idle, no macro running, no window movement) against the v1.2.0 baseline. If idle CPU rises measurably (e.g. layered blur regions constantly recomposited during scroll), the fallback is to **reduce blur layer count** (e.g. blur only the sidebar and the topmost banner, not every individual card) rather than drop translucency entirely — this preserves UI-01/UI-02's visual goal while protecting UI-04.

## Action-Type Model (D-10 resolution)

**Decision: keep TWO selectors, not a unified 4-item flat list.**

The backend's real model (`src-tauri/src/state/mod.rs`) is `ActionStep` (input type: mouse button or key) crossed with `TriggerMode` (Pulse or Hold) — `Hold` is a *mode* that can apply to ANY input type, not a peer item in a flat list. A single unified 4-item dropdown (`Left Click / Right Click / Hold / Key Press`) cannot represent "Hold + Key" or a hypothetical future "Hold + Right Click" without inventing a 5th+ combinatorial item, and would misrepresent the data model to the user. Two selectors — restyled with unambiguous labels — both satisfies UX-10's literal label requirement and stays truthful to the backend.

| Selector | Options (exact labels, UX-10 compliant) | Notes |
|----------|------------------------------------------|-------|
| **Input** (was "Action type" ambiguity) | `Left Click`, `Right Click`, `Middle Click`, `Key Press` | **`Key Press` is net-new this phase (D-11)** — the dropdown currently only offers the 3 mouse buttons (`App.tsx:1111-1113`); `InputEvent::Key` already exists in the type system and is rendered elsewhere (`formatInputEvent`) but was never selectable. Selecting `Key Press` reveals the key-capture widget inline (see D-12 below) in place of the interval-ms field's neighbor. |
| **Mode** | `Pulse (Repeat)`, `Hold (Sustained)` | Relabeled from the current `⏱ Pulse (Interval)` / `🔒 Hold (Latched)` — "Latched" tested as jargon; "Sustained" reads clearer paired with "Hold" and matches this UI-SPEC's own `RunningState` terminology ("held") already shown on cards since Phase 9. |

**Selecting `Key Press` as Input:**
- The interval-ms numeric field is hidden/disabled when `Mode = Hold (Sustained)` (a held key doesn't repeat — same rule already implicit for mouse buttons today).
- **D-12: the key-capture widget is the EXACT SAME component already shipped in Phase 8 for hotkey trigger-key binding** (modifier chips, keydown capture, Escape-to-cancel — Phase 8 UI-SPEC C-5 `ModifierPreviewChip` + capture chip). No new key-picker component is built. Visually it renders in the same slot the "🖱 Left/Right/Middle Click" dropdown occupied, once `Key Press` is selected as the Input.
- This reuses `startCapture()` (already in `App.tsx`) with a distinct `onCommit` callback that writes to the macro's `ActionStep`'s `Key` field instead of the trigger-key fields — this is a wiring detail for the planner, not a new visual component.

**Both create form AND inline card-edit form use this identical two-selector pattern** (D-13 requires the edit form to reuse the same fields/components as creation).

**Structure:** single icon button, `text-base` glyph that cycles `🖥 → ☀ → 🌙 → 🖥`. Click handler advances `automux.theme_preference` through `"system" → "light" → "dark" → "system"`.

**Exact classes:** `flex flex-col items-center gap-1 px-2 py-3 rounded-lg cursor-pointer text-text-muted hover:text-text-main transition-colors w-16` (no accent tint — this is a utility control, per the "Accent is NOT used for" rule).

### C-D1. Inline delete confirmation (D-14, new — replaces `window.confirm()`)

**Location:** replaces the macro card's header row content **in place** when delete is initiated — the card does not disappear or get replaced by a separate element; its header row swaps to a confirmation state. This mirrors D-13's "no modal, inline expand-in-place" philosophy exactly, applied to delete instead of edit.

**Trigger:** clicking the existing `✕` delete icon button sets a per-card signal (e.g. `confirmingDeleteId()`) instead of immediately calling `window.confirm()` / `remove_macro`.

**Structure (replaces the card's normal header row while confirming):**
```text
┌─────────────────────────────────────────────────────┐
│ Delete "AFK Farm"?                                   │
│ This can't be undone.            [Cancel]  [Delete]  │
└─────────────────────────────────────────────────────┘
```
**Exact classes:**
- Container: same card padding as normal (`glass-card p-4`), but header content swaps to `flex items-center justify-between`.
- Heading: Heading-role typography (15px/600), `text-text-main`.
- Body: Body-role typography (13px/400), `text-text-dim`.
- `Cancel` button: neutral, `px-2.5 py-1 rounded-md text-[11px] font-semibold bg-surface-alt border border-border text-text-muted hover:text-text-main transition-colors cursor-pointer`.
- `Delete` button: destructive, `px-2.5 py-1 rounded-md text-[11px] font-semibold bg-danger/10 text-danger border border-danger/20 hover:bg-danger/20 transition-colors cursor-pointer` (same visual weight as the existing delete icon button's danger tint, just with a text label instead of `✕` in this confirming state).

**Dismissal:** `Cancel` click, clicking elsewhere on the card (optional — planner's call whether to wire an outside-click dismiss; not required for UX-08 correctness), or successful `Delete` click (card is removed from the list entirely via the existing `remove_macro` IPC + `state-changed` broadcast — no local removal needed).

### C-E1. Inline macro edit (D-13, new — the primary UX-09 surface)

**Location:** the macro card expands in place when the `✎` edit icon button is clicked. The card's normal display rows (name, target/trigger meta, step chips) are replaced by the SAME form fields used in the "New Macro" creation form (name input, Input selector, Mode selector, interval field or key-capture widget, target-app select), pre-populated with the macro's current values.

**Trigger:** new `✎` icon button, placed to the LEFT of the existing `✕` delete button in the card header's action-icon cluster (`flex items-center gap-1.5`), same visual weight/size as the delete button but neutral-tinted (`text-text-muted`, not `text-danger`):
```
class="px-2.5 py-1 rounded-md text-[11px] font-semibold transition-colors cursor-pointer
       bg-surface-alt border border-border text-text-muted hover:text-text-main hover:border-border-hover"
title="Edit macro"
```

**Structure while editing:** identical field set/order to the New Macro form (name → Input selector + interval-or-key-capture → target-app select → Mode selector), with `Save Changes` (accent primary CTA) and `Cancel` (neutral secondary) buttons where "Create Macro" sits in the creation form.

**Fields covered (UX-09 requirement — name, action type, key/button assignment, timing):**
- Name → existing name input, pre-filled.
- Action type (Input + Mode selectors) → pre-filled from `macro.sequence.steps` / `macro.trigger_mode`.
- Key/button assignment → pre-filled trigger-key chip (reuses the same capture widget as creation, per D-12) AND, if Input = Key Press, the action-step's own key value uses the same capture widget in its own slot (two independent key-capture instances can coexist on one card — this is a wiring detail, not a new visual component).
- Timing → pre-filled interval-ms field (hidden when Mode = Hold, matching the Action-Type Model section above).

**Mutual exclusion with other in-progress edits:** only one card may be in edit mode (or delete-confirm mode) at a time — opening edit on card B while card A is mid-edit cancels card A's edit without saving (discard, no confirmation needed since nothing was persisted yet). This mirrors the existing `editingCardId()`/`editingField()` signal pattern already used for the target-app and trigger-key inline editors.

**Persistence:** `Save Changes` calls the backend update path (planner/researcher to confirm exact `Intent`/IPC shape — likely a new `Intent::UpdateMacro` consolidating `set_macro_target_app`, `set_macro_sequence`, `set_macro_trigger_key`, name, and trigger_mode into one call, OR sequential calls to the existing per-field IPC commands; this is an implementation decision for RESEARCH.md / the planner, not a visual contract concern). On success, the card collapses back to its normal display state showing the new values. On failure (e.g. hotkey conflict), the existing `ConflictErrorToast` (Phase 8 C-1) fires and the edit form stays open so the user can correct it.

## Interaction Contract

### UX-08 — Delete macro (already shipped Phase 9, this phase restyles the confirmation UX per D-14)

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Clicks `✕` delete icon on a macro card | Card header swaps to **C-D1** inline confirmation state |
| 2 | User | Clicks `Delete` | `remove_macro` IPC fires; on success the card is removed from the list via the next `state-changed` broadcast |
| 2alt | User | Clicks `Cancel` (or, if wired, clicks elsewhere) | Card header reverts to normal display state, no IPC call made |

### UX-09 — Edit macro (net new)

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Clicks `✎` edit icon on a macro card | Card expands in place into **C-E1**, pre-filled with current values |
| 2 | User | Changes any field (name, Input, Mode, key/button, interval, target app) | Standard controlled-input behavior, local form state only — no IPC yet |
| 3 | User | Clicks `Save Changes` | Update IPC call(s) fire; on success, card collapses to normal display with new values |
| 3alt | Backend | Returns a conflict error (e.g. hotkey already bound) | **Phase 8 C-1** `ConflictErrorToast` fires; edit form stays open, user corrects and retries |
| 4alt | User | Clicks `Cancel` at any point | Card collapses to normal display; all local edits discarded, no IPC call made |

### UX-10 — Unambiguous action-type labels

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Opens the Input selector (create or edit form) | Dropdown shows exactly 4 labeled options: `Left Click`, `Right Click`, `Middle Click`, `Key Press` — no unlabeled/icon-only options |
| 2 | User | Selects `Key Press` | The mouse-button dropdown's neighbor slot swaps to the key-capture widget (reused from Phase 8, per D-12) |
| 3 | User | Opens the Mode selector | Dropdown shows exactly 2 labeled options: `Pulse (Repeat)`, `Hold (Sustained)` |

### Theme toggle

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | App boot | Reads `localStorage.automux.theme_preference`; if unset/`"system"`, resolves via `matchMedia("(prefers-color-scheme: dark)")` | `data-theme` attribute set before first paint |
| 2 | User | Clicks the sidebar theme toggle | Cycles `system → light → dark → system`; `localStorage` updated; `data-theme` updates immediately, no reload required |
| 3 | OS | User changes OS-level appearance while AutoMux preference is `"system"` | `matchMedia` `change` listener updates `data-theme` live |

## Accessibility & Visual Hierarchy

| Concern | Contract |
|---------|----------|
| Sidebar nav without visible page title elsewhere | Each nav item shows BOTH icon and text label (never icon-only) — addresses the icon-only-nav accessibility gap directly, per this phase's own sidebar design (no reliance on `title` attribute alone for primary navigation). |
| Focus rings | Carried forward from Phase 8: new buttons inherit `focus:outline-none` from existing form-field convention; no custom ring added to sidebar nav items, edit/delete buttons, or theme toggle — consistent with existing app-wide pattern (click-target-only, no visible focus ring on non-form controls). |
| Color-only state | Every status indicator continues to pair color with text (unchanged Phase 7/8/9 pattern). The new Edit/Delete icon buttons pair color (neutral vs. danger) with distinct glyphs (`✎` vs `✕`) AND `title` tooltips — never color alone. |
| Keyboard nav | Sidebar nav items are real interactive elements (buttons, not divs) so they are natively tab-reachable; UI-02's "keyboard-navigable" requirement is satisfied via native tab order — no custom roving-tabindex widget is introduced (out of scope complexity for a 2-item + 1-toggle rail). |
| Screen reader | Sidebar nav item text labels are real DOM text (not `aria-label`-only), same for Edit/Delete buttons' `title` attributes. Theme toggle should additionally carry an `aria-label` stating the action it will perform next (e.g. `aria-label="Switch to light theme"`) since its glyph alone changes meaning across the 3-state cycle — a `title` tooltip alone is insufficient for a control whose function changes state to state. |
| Reduced motion | The existing `pulse-glow` animation (`App.css`) is preserved unchanged. No new animations are introduced by the sidebar or theme toggle (state changes are instant, no transition animation on `data-theme` swap, to avoid a jarring color-animation flash). Card expand/collapse (edit, delete-confirm) MAY use a simple height/opacity transition (`transition-all duration-150`) consistent with the existing `.glass-card` hover transition timing — this is a nice-to-have, not a contract requirement, and must respect `prefers-reduced-motion` if implemented (skip the transition, snap instantly). |
