<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Frontend signal → DOM render | SolidJS signals (`conflictError`, `state.conflicts`, `showGlobalNotice`, `recordingModifiers`) drive JSX. A stale signal can render a wrong value (e.g., a dismissed toast reappearing on next state-changed). |
| `localStorage` flag → first-run banner | The C-3 banner's visibility is gated by a single key in `localStorage`. The user can edit it via dev tools. |
| `modifierChips` bit order → chip render | The semantic order (Shift → Ctrl → Alt → Cmd/Win) is hard-coded; a misordered array would render modifiers in the wrong order. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|----------------|
| T-08-25 | Tampering | `localStorage.automux.hotkey_global_notice_dismissed` modified by user | accept | The flag is advisory. Tampering with it can re-show the banner (acceptable: a one-time educational message is not security-critical). RESEARCH.md R-8 explicitly chose `localStorage` over a backend sentinel for this reason. |
| T-08-26 | Information Disclosure | C-2 conflict body lists macro names | accept | By design per UX-12. The user must know which macros overlap. The names come from `state().macros` which is already in the frontend. |
| T-08-27 | Spoofing | C-5 chip display | mitigate | The chip order is hard-coded (Shift → Ctrl → Alt → Cmd/Win) — same on both platforms. Press order does not affect display order. The bit values are pinned by Rust unit tests. |
| T-08-28 | Denial of Service | Re-render storm on `state-changed` | accept | The `For` over `state().conflicts` only re-renders when the array reference changes. SolidJS's fine-grained reactivity means only the changed conflict card re-renders. No infinite loop. |
| T-08-29 | Repudiation | Dismissed conflict toast comes back if a new conflict arrives | accept | The 8-second timer is single-slot — a new `showConflictError` call replaces the timer and the toast. This is the intended UX: the user is told about the latest conflict. |
| T-08-30 | Elevation of Privilege | `conflictsDismissed` is session-only | accept | Per UI-SPEC C-2: dismissing is per-session; the warning reappears on the next conflict. No persistence required. |
| T-08-SC | Tampering | npm/pip/cargo installs | mitigate | No new npm packages. slopcheck gate not relevant. |
</threat_model>
