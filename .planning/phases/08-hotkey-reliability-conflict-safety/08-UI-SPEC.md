# Phase 8 — UI Design Contract

> Visual and interaction contract for Phase 8 (Hotkey Reliability & Conflict Safety). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This phase adds four frontend surfaces on top of the existing SolidJS + Tauri 2 + Tailwind 4 app. No design system introduction, no framework change, no new color tokens. All new UI reuses the existing `glass-card`, toast, and warning-banner patterns already shipped in Phases 1–7.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Tailwind CSS 4 + custom `@theme` tokens; SolidJS project, **shadcn is not applicable**) |
| Preset | not applicable |
| Component library | none (no Radix, no Base UI, no Ark UI — SolidJS project) |
| Icon library | none — inline glyphs/emoji only (⚠ ✓ ✕ ↗ 🎯 ⌨ 🖱 ⏱ 🔒 🌐 📁) to match existing convention |
| Font | `Inter, ui-sans-serif, system-ui, sans-serif` (declared as `--font-sans` in `App.css:5`) |

**Why no shadcn:** project is SolidJS. shadcn targets React. The Tailwind 4 `@theme` block in `App.css:4-22` is the project's design-system source of truth and already exposes every token required for this phase.

## Component Inventory

Each new or modified component, with its location, role, and exact visual specification.

### C-1. `ConflictErrorToast` (new)

**Location:** top of `<main>`, just below the tab bar, ABOVE the auto-save banner. Rendered when `conflictError() !== null`.

**State signal:** `const [conflictError, setConflictError] = createSignal<{ key: string; macroName: string } | null>(null);`

**Structure:** clone the profile message toast (`App.tsx:1062-1076`) but with **red styling** and an 8-second auto-dismiss.

```text
┌─────────────────────────────────────────────────────────────┐
│ ✕  Hotkey already bound                                     │
│    F5 is already assigned to "AFK Farm". Unbind it first     │
│    or pick a different key.                       [Dismiss] │
└─────────────────────────────────────────────────────────────┘
```

**Exact classes (Tailwind 4):**
- Container: `rounded-lg px-4 py-2.5 text-xs font-medium flex items-center gap-2 transition-all bg-danger/10 text-danger border border-danger/20`
- Icon: `<span>✕</span>` (matches the profile error toast, not the auto-save warning `⚠`).
- Body: two lines — bold heading + dim body using `text-text-dim` (NOT `text-danger` — body text is muted to reduce alarm density, only the heading and icon are danger-tinted).
- Dismiss button: `text-[11px] text-text-muted hover:text-text-main transition-colors duration-200 cursor-pointer`.

**Trigger sites (each must `setConflictError({...})` on caught error):**
- `handleCreateMacro` (currently `console.error` at `App.tsx:327`).
- `handleCardSetTriggerKey` (currently `console.error` at `App.tsx:383`).
- Any new code path that calls `bind_hotkey`, `set_macro_trigger_key`, or `add_macro` with a `trigger_key`.

**Auto-dismiss:** `setTimeout(() => setConflictError(null), 8000)`. The `setTimeout` id must be cleared if a new conflict arrives before the timer expires.

### C-2. `ConflictWarningRegion` (new)

**Location:** between the engine card / active-app / profile-badge block and the `Macros` section header. Sits **above** the existing "Auto-Save Error Banner" position (`App.tsx:715`).

**State signal:** `const [conflictsDismissed, setConflictsDismissed] = createSignal(false);` (re-enabled when `state().conflicts.length` changes from 0 → >0).

**Visibility:** `<Show when={state()?.conflicts && state()!.conflicts.length > 0 && !conflictsDismissed()}>`.

**Source data:** `state().conflicts: { macros: string[]; input: InputEvent }[]` — derived field added to `AppState` in RESEARCH.md §3.2. The macro IDs are looked up against `state().macros[id].name` for display.

**Structure:** one warning card per conflict. Use the **auto-save warning banner structure** (`App.tsx:716-735`) as the template, but for each conflict:

```text
┌─────────────────────────────────────────────────────────────┐
│ ⚠  2 macros are injecting the same input         [Dismiss] │
│    "AFK Farm" and "Boss Spam" both inject Left Click —     │
│    clicks will fire at 2× rate.                            │
└─────────────────────────────────────────────────────────────┘
```

**Exact classes (Tailwind 4):**
- Container: `bg-warning/10 border border-warning/20 rounded-lg p-3 flex items-center gap-3`
- Icon: `<span class="text-warning text-base">⚠</span>` (matches `App.tsx:721`).
- Heading: `<p class="text-xs font-medium text-warning">` (mirrors `App.tsx:723`).
- Body: `<p class="text-[11px] text-text-dim">` (mirrors `App.tsx:724`).
- Dismiss button: identical to the auto-save dismiss at `App.tsx:728-732`.

**Multi-conflict rendering:** if `state().conflicts.length > 1`, render one card per conflict, stacked vertically with `gap-3` (matches the engine/permissions row pattern at `App.tsx:539`).

**When the conflict disappears (e.g., user disables one macro):** the next `state-changed` event delivers `conflicts: []`. The component re-renders to nothing. The `conflictsDismissed` signal is reset to `false` automatically because the `<Show>` predicate requires `length > 0`. No explicit reset is needed.

### C-3. `FirstRunGlobalNotice` (new)

**Location:** between the `Active Profile Badge` and the `Auto-Save Error Banner` (i.e., between `App.tsx:713` and `App.tsx:715`). Sits above the macros section.

**State signal:** `const [showGlobalNotice, setShowGlobalNotice] = createSignal(false);` — set in the initial-fetch `createEffect` based on `localStorage.getItem("automux.hotkey_global_notice_dismissed") !== "1"`.

**Structure:** mirror the auto-save error banner (`App.tsx:716-735`) but with **info-tinted styling** (no warning tint, no danger tint — the message is informational, not an error).

```text
┌─────────────────────────────────────────────────────────────┐
│ 🌍  Binds are system-wide                          [Got it] │
│     Hotkeys fire even when AutoMux is in the background.    │
└─────────────────────────────────────────────────────────────┘
```

**Exact classes (Tailwind 4):**
- Container: `bg-accent/10 border border-accent/20 rounded-lg p-3 flex items-center gap-3` (reuses the accent-tinted chip style at `App.tsx:710`).
- Icon: `<span class="text-accent text-base">🌍</span>` (a new emoji glyph; matches the emoji convention used elsewhere — `App.tsx:711, 790-792, 836-837, 944, 1120`).
- Heading: `<p class="text-xs font-medium text-accent">`.
- Body: `<p class="text-[11px] text-text-dim">`.
- Dismiss button: identical to the auto-save dismiss at `App.tsx:728-732`, but copy is `Got it`.

**Persistence contract:**
- Dismiss click: `localStorage.setItem("automux.hotkey_global_notice_dismissed", "1")` then `setShowGlobalNotice(false)`.
- Initial check (inside the existing `createEffect` at `App.tsx:135-165`, after the `setAppVersion` line): `setShowGlobalNotice(localStorage.getItem("automux.hotkey_global_notice_dismissed") !== "1")`.
- This is a frontend-only flag. If the user clears app data, the banner reappears — by design (per RESEARCH.md R-8: false-positive re-show is cheaper than false-negative never-show).

### C-4. In-card "Global" subtitle (UX-14) (new, inline edit)

**Location:** inline inside the existing trigger-key chip block, immediately after the trigger-mode suffix `({macro.trigger_mode})` at `App.tsx:1033-1035`. Renders in BOTH the bound-key branch and the unset-key branch (so the user sees the statement even before binding a key).

**Structure (bound-key branch, replaces the closing `</div>` of the existing key-chip wrapper at `App.tsx:1001-1037`):**

```tsx
<div class="flex items-center gap-1">
  {/* existing chip + Press…/trigger_mode code unchanged */}
  <span class="text-[10px] text-text-muted">({macro.trigger_mode})</span>
  <span class="text-[10px] text-text-dim">↗ Global</span>
</div>
```

**Unset-key branch (add after the `({macro.trigger_mode})` at `App.tsx:997-999`):**

```tsx
<div class="flex items-center gap-1">
  <span class="px-1.5 py-0.5 rounded border border-dashed border-border text-[10px] font-mono text-text-dim cursor-pointer hover:border-accent/40 hover:text-text-main">
```

**Exact classes for the new subtitle:** `text-[10px] text-text-dim` — same as the version string at `App.tsx:504` and counts at `App.tsx:743, 1111`. Deliberately the dimmest text color to avoid visual noise; the message is informational, not a call to action.

**No dismiss.** Persistent across renders, across sessions, and across profile loads. This is the "always-visible ground truth" per RESEARCH.md D-6.

### C-5. `ModifierPreviewChip` (new, in-capture widget)

**Location:** replaces / extends the existing key-capture chip at `App.tsx:839-879` (new-macro form) and the card-edit chip at `App.tsx:1000-1037`. Only shows during the `triggerKeyRecording` state.

**State signal:** add `const [recordingModifiers, setRecordingModifiers] = createSignal<number>(0);` (set/cleared in the `startCapture` listener).

**Display logic:** during capture, render the current modifier state in a row of small chips ABOVE the key name. Example for `Cmd+F5` being captured while the user holds Cmd:

```text
┌──────────────────────────────────────────┐
│ ⌘                                        │  ← modifier chips row
│ ┌─────────────┐  Press a key…    [✕]     │  ← existing capture chip
│ └─────────────┘                          │
└──────────────────────────────────────────┘
```

**Exact classes for the modifier chip row:**
- Container: `flex items-center gap-1 mb-1` (just above the existing capture widget, separated by `mb-1` to match the existing micro-spacing at `App.tsx:1037`).
- Each chip: `px-1.5 py-0.5 rounded bg-surface-alt border border-border text-[10px] font-mono text-text-main` — reuses the bound-key chip styling at `App.tsx:1006` with the bound-key's `text-text-main` color (because these chips are user-input feedback, not labels).

**Modifier symbol map (platform-agnostic values, no `IS_MACOS` branching in the label text — only in the symbol):**

| Bit (macOS / Windows) | Symbol |
|------------------------|--------|
| 0x100000 / 0x0008 | `⌘` (macOS) / `Win` (Windows) |
| 0x80000 / 0x0001 | `Option` (macOS) / `Alt` (Windows) |
| 0x40000 / 0x0002 | `Control` (macOS) / `Ctrl` (Windows) |
| 0x20000 / 0x0004 | `Shift` (both) |

**Display order:** `Shift → Ctrl → Alt → Cmd/Win` (left to right). Do not show chips for unset bits; render only the bits that are currently set in `recordingModifiers()`.

**At commit time (when the user releases a non-modifier key):** the final chip display updates to show the committed combo, e.g., `⌘+F5` or `Ctrl+Shift+F5`. Use the same `font-mono` `text-[10px]` chip pattern as the bound-key display at `App.tsx:1006`, but render two chips in a row: modifier chips first, then the key chip. Example final state:

```text
⌘  F5
```

(Rendered as two `text-[10px] font-mono` chips in a `flex items-center gap-1` row.)

**Modifier label resolution in `resolveKeyName`:** when the user binds a pure modifier (e.g., Shift), the existing `App.tsx:357` filter is REMOVED only for modifiers that have a complete match (per RESEARCH.md Open Questions #1 — modifier-only binds remain blocked for this phase). The filter stays. However, the lookup tables in `keymap.ts` already have modifier names (e.g., `CGKEYCODE_TO_NAME[56] = "Shift"`, `VK_TO_NAME[0x10] = "Shift"`), so a future phase that enables modifier-only binds does not need a keymap change.

### C-6. `resolveKeyName` updates (modify `keymap.ts` only)

**No structural change to `keymap.ts`.** The existing `CGKEYCODE_TO_NAME` and `VK_TO_NAME` tables already cover all keys the user can bind (A–Z, 0–9, F1–F12, arrows, navigation, modifiers, numpad on Windows). Per RESEARCH.md §3.3 Gap 2, **numpad-on-macOS is not required for UX-13 success** and is out of scope.

The contract is:
- The function signature is unchanged: `resolveKeyName(nativeCode: number): string`.
- The fallback `Key {nativeCode}` (line 195) is preserved for any future unmapped code.
- Numpad keys on Windows render as `Num 0` … `Num 9` (existing entries at `keymap.ts:164-166`).

## Interaction Contract

### UX-11 — Hotkey conflict (binding a key already in use)

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Clicks a macro card's `Set key…` or `F5` chip to re-bind | C-5 capture widget opens |
| 2 | User | Presses the new key (e.g., `F5` while macro A is already bound to F5) | C-5 chip shows "F5" while `recording` |
| 3 | User | Clicks confirm / presses Enter / clicks outside (any commit path) | `handleCardSetTriggerKey` invokes `bind_hotkey` + `set_macro_trigger_key` |
| 4 | Backend | Detects conflict (per RESEARCH.md D-2), returns `Err("Hotkey F5 is already bound to macro {id}. Unbind it first or pick a different key.")` | n/a |
| 5 | Frontend | `try/catch` catches the error, calls `setConflictError({ key: "F5", macroName: "AFK Farm" })` | **C-1** toast appears at the top of the scroll area, danger-tinted, 8s auto-dismiss |
| 6 | User | Reads the toast, chooses to either unbind from the other macro or pick a different key | UI returns to the unbound / unchanged state — the conflicting binding was NOT applied |

**Self-rebind exemption (RESEARCH.md D-4):** if the user re-binds the same macro to the same `(keycode, modifiers)`, the backend returns `Ok(())` and no toast appears.

### UX-12 — Same-input overlap (two enabled macros inject the same input)

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Toggles on a second macro (macro B) that injects the same input as an already-enabled macro (macro A) | macro B toggle flips to ON, `state-changed` event arrives |
| 2 | Backend | `recompute_conflicts()` finds the overlap, returns `AppState { conflicts: [{ macros: [A, B], input: MouseButton Left }, ...] }` | n/a |
| 3 | Frontend | `state()` updates via `setState` from the event listener at `App.tsx:169-175` | **C-2** conflict warning region renders one card per conflict |
| 4 | User | Reads the warning — sees macro names, the conflicting input, the rate multiplier | no action required; the macros still run |
| 5 | User | Either dismisses the warning (sets `conflictsDismissed = true` for this session) OR resolves the conflict by disabling one macro | if conflict is resolved, next `state-changed` arrives with `conflicts: []` and the warning disappears; if dismissed, the warning reappears on the next conflict |

**Non-blocking guarantee:** the macros continue firing in the background. The warning is informational only — RESEARCH.md §3.2 confirms this is the explicit design.

### UX-13 — Modifier-aware key capture

| Step | Actor | Behavior | UI surface |
|------|-------|----------|------------|
| 1 | User | Clicks the trigger-key chip in the new-macro form (or in a card) | `startCapture` attaches the `keydown` listener; `setTriggerKeyRecording(true)` |
| 2 | User | Holds `Cmd` (macOS) or `Ctrl` (Windows) | `recordingModifiers` signal updates; **C-5** modifier chip `⌘` (or `Ctrl`) appears above the key-capture widget |
| 3 | User | Holds `Shift` in addition | C-5 now shows two chips: `Shift ⌘` (semantic order, not press order) |
| 4 | User | Presses `F5` (non-modifier) | C-5 commits: the modifier chips plus the key chip are rendered; the IPC call fires with `modifiers: <bitmask>` and `keycode: <native F5 code>` |
| 5 | Backend | Receives the binding, runs the conflict check, returns `Ok(())` or `Err(...)` | n/a |
| 6 | Frontend | Resets `setTriggerKeyRecording(false)`, displays the final `⌘+F5` combo on the macro card | trigger-key chip renders the multi-chip display |

**Key capture rejection rules (no UI change for these — preserve current behavior):**
- Pure-modifier press (e.g., user holds `Shift` only and releases): the existing `App.tsx:357` filter blocks it; no binding is made. The recording widget remains open. UX-13 success criterion is satisfied (A–Z, 0–9, F1–F12, modifier **combinations** — modifier-only is an edge case per Open Questions #1).
- Escape keypress: existing `App.tsx:351-355` behavior — cancels capture.

## Accessibility & Visual Hierarchy

This phase reuses the existing patterns, so no new a11y work is required beyond the existing keyboard / focus / screen-reader support that Phase 7 shipped.

| Concern | Contract |
|---------|----------|
| Focus rings | All new buttons inherit the default `focus:outline-none` from existing form fields. For the new banner dismiss buttons, **do not** add a custom ring — the existing pattern at `App.tsx:730` has no explicit focus ring (it relies on browser default for click targets). To match, the new buttons also skip a custom ring. |
| Color-only state | Every status indicator pairs color with a text label (e.g., red dot + "Denied" text). The new conflict toast pairs red background with the heading "Hotkey already bound" + the body text. No color-only signaling. |
| Keyboard nav | The existing capture widget is keyboard-only by design (it captures `keydown`). The new C-5 modifier chips are display-only and not interactive — they do not need focus rings. |
| Screen reader | The trigger-key chip's `↗ Global` subtitle is plain text inside a `<span>`, which screen readers will read aloud. The first-run banner and conflict region use semantic text. No `aria-live` is added; the toast and banners are static (the user already performed the action that triggered them). |
| Reduced motion | The existing `pulse-glow` animation at `App.css:67-74` is preserved. No new animations are added in this phase. |
